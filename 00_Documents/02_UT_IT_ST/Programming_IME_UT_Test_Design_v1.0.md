## 1. 测试对象与实施原则（単体試験方針）

- 测试对象：`pime-core`、`pime-rules`、`pime-context`、`pime-edit`、`pime-ai-worker` 的**纯逻辑/局部状态**与边界解析；Windows 依赖通过明确 Fake 端口替身注入。包括七语言规则、UTF-16、Diff/版本、Effort、安全过滤、配置迁移。
- 主要技术：Rust `cargo test` 的 unit/integration tests（此处“integration tests”指 Rust 测试组织形式，按验证对象仍归入本项目 UT）、property-based tests、fuzzing（可选）、虚拟时钟、Fake Vault/Provider/Bridge；**不能通过真实云 API 的不稳定返回评判单位函数**。
- 覆盖基线：所有 P0 纯逻辑功能有正常/边界/异常用例；安全关键函数的所有分支和错误返回需覆盖；建议全工程语句覆盖≥80%，安全核心分支覆盖 100%（项目拟定目标，实际统计需执行后填写）。
- 计量：对算法性能目标使用固定 CPU/构建模式/输入 Fixture；性能 UT 是诊断辅证，正式 P95 以 ST 受控测量为准。
- 准入：详细设计、接口 Schema、语言包 Fixture 与版本已冻结；退出：P0 用例全部通过，关键安全断言全部通过，阻断级问题为零。

| FX-SECRET-01 | 完全虚构的 Key、`.env` 与 PRIVATE KEY 头 | 零泄露/明确阻断或脱敏 |

| 执行结果 | 未执行（`Not Run`） |

## 4. 执行记录与缺陷处理（実施記録・不具合管理）

用例执行时记录：`test_id`、环境 ID、构建 Commit/hash、Fixture SHA-256、开始/结束时间、操作者、自动化 job、预期与实际、截图/日志路径、缺陷单号与复测状态。所有未执行项保持 `Not Run`，不得默认视为 `Pass`。

- 判定：`Pass`（全部期待成立）、`Fail`（任一关键断言失败）、`Blocked`（环境/前置条件缺失）、`Not Run`、`Not Applicable`（须写批准理由）。
- 对关键问题使用 `Stop Ship`：文件内容非授权修改、Key/源码外泄、密码框上传、重复编辑、原始输入丢字或原系统输入法遭损坏。
- P0 通过率计算时**Blocked/Not Run 不计 Pass**；只有在对应环境完成全部 P0 后才能签署相应测试层级。
- 功能追踪用 Excel 的 `Requirements` 与 `{level}_Cases` 工作表；变更要求必须同步更新受影响 DD/测试和期待结果。

## 5. 设计审查清单（レビュー項目）

1. 每条用例是否具备稳定的前提、操作、输入数据、可断言的预期结果和证据路径？
2. 是否包含正常、异常、边界、安全、并发/超时或退化路径，而不是只测试成功路径？
3. 测试层级是否正确：UT 针对算法，IT 针对接口，ST 针对系统与用户场景？
4. 需要真实 Windows/Provider/编辑器的部分是否明确标出，未把 Mock 通过冒充实测？
5. 所有涉及文件修改/外送的场景，是否确认未授权时零写入、零外发及可恢复？
