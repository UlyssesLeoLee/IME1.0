# LRU 缓存（LRU Cache）

- 资产 ID：`algorithm.datastructure.lru_cache`
- 类型：`algorithm`（算法）
- 分类：`datastructure`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`lru_cache`、`LRU`、`最近最少使用缓存`、`least recently used`

## 一句话定位

哈希表负责按 key 找到节点，双向链表负责按"最近使用顺序"排列，两者的配合让每次读写都是 O(1)。

缓存满了要决定淘汰谁，LRU 的直觉最自然，但"维护使用顺序"如果用 Vec 实现会是 O(n)。

## 典型源文件形状

```rust
use std::collections::HashMap;

pub struct LruCache<K, V> {
    map: HashMap<K, *mut Node<K, V>>,   // 或用 index-based 链表避免裸指针
    head: Option<usize>,
    tail: Option<usize>,
    capacity: usize,
}

// 命中时：把节点从链表原位置摘下，移到最前（最近使用）
// 未命中且已满：淘汰尾部（最久未使用）
```

## 适用条件

- 需要 O(1) 的查找与淘汰顺序维护
- 工作集有明显的时间局部性
- 缓存容量固定且可估
- 作为本地缓存层（配合旁路缓存模式）

## 反例

- 命中率不敏感——FIFO 或随机淘汰同样可用
- 需要按频率淘汰——用 LFU 或 ARC（抗扫描污染）
- 缓存条目很大且数量不定——应考虑只缓存索引或加磁盘层
- 需要 TTL——LRU 不含时间语义，要额外记录过期时间

## 并发风险

- LRU 缓存是典型的并发热点：每次读写都要改链表顺序
- 用 `Mutex` 保护整体结构最简单，但会成为多线程瓶颈；分段缓存（sharded cache）可降低竞争
- Rust 中可用 `RwLock`（读多写少时）但 get 命中也要写（移动位置），实际是写多
- 跨线程共享时推荐成熟的并发 LRU 实现（如 `lru` crate 的并发版本），避免自己写锁逻辑出错
- 淘汰时若回调释放资源（如关闭连接），要避免在持锁期间调用外部代码

## 替代方案

- `algorithm.datastructure.hash_table` — LRU 内部就有哈希表；只需要查找不需要淘汰顺序时用哈希表即可。
- `pattern.integration.cache_aside` — LRU 是缓存实现，旁路缓存是缓存使用策略，两者常配合使用。

## 测试说明

- 命中后该条目应变为"最近使用"
- 超过容量时淘汰最久未使用的条目
- 访问已存在 key 并更新值（不应增加条目数）
- 容量为 0 的边界行为
- 随机操作序列与参考实现（用 Vec + sort 按计数）交叉比较
- 并发测试：多线程读写下命中率与条目数不变量成立

## 实现注意

- 优先标准库/成熟库：Rust 标准库没有 LRU；成熟 crate 有 `lru`、`quick_cache` 等，引入前需核查许可与维护状况
- 复杂度：get/put O(1)，空间 O(容量)；淘汰 O(1)
- 稳定性：不适用
- 内存：哈希表 + 链表节点，约每个条目 2-3 倍的键值内存开销
- 溢出：容量与计数用 `usize`；哈希种子要固定（同一进程内一致即可）
- 极端输入：容量 0、容量 1、键值极大、频繁命中同一键
- 并发安全：必须同步；推荐成熟并发实现或分段缓存
- 限制：只按最近使用淘汰，不感知频率与成本；无 TTL 与预取
