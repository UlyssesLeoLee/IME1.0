# 备忘录（Memento）

- 资产 ID：`pattern.gof.behavioral.memento`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Memento`、`备忘录模式`、`memento pattern`

## 一句话定位

把对象某一时刻的内部状态封成一枚"快照"，让对象自己决定如何存取，从而支持撤销、存档与时间旅行调试。

编辑器的撤销栈、游戏的存档、编辑器的"回到上次保存"都需要状态快照，但直接对外暴露字段会破坏封装。

## 典型源文件形状

```rust
pub struct Editor { text: String, cursor: usize }

#[derive(Clone)]
pub struct EditorSnapshot { text: String, cursor: usize }

impl Editor {
    pub fn snapshot(&self) -> EditorSnapshot {
        EditorSnapshot { text: self.text.clone(), cursor: self.cursor }
    }
    pub fn restore(&mut self, snap: EditorSnapshot) {
        self.text = snap.text; self.cursor = snap.cursor;
    }
}
```

## 适用条件

- 需要撤销/重做或定期存档
- 状态是对象的私有实现细节，不希望外部读取或修改
- 快照的粒度与时机由对象自己决定
- 需要把"历史"交给调用方管理（调用方只持有不透明快照）

## 反例

- 对象是纯值类型且可整体克隆——直接 `clone` 更简单
- 状态包含不可克隆资源（句柄、连接）——快照会变得昂贵或不可行
- 快照频率很高且状态很大——内存与 GC 压力会明显上升，应考虑增量或差分快照
- 需要跨版本恢复历史状态——纯值快照会因结构变化而失效，需考虑序列化格式

## 并发风险

- 快照通常是纯数据，天然可跨线程共享；但若包含 `Rc`/裸指针则不满足 `Send`
- 生成快照与修改状态之间若没有同步，可能拍到不一致的中间状态——应在同一临界区内完成
- 历史栈是共享可变状态时需要 `Mutex`；撤销操作应与状态修改串行化
- 撤销栈在多线程编辑器里要明确归属：通常是单线程拥有，或用命令队列串行化

## 替代方案

- `pattern.gof.behavioral.command` — 命令记录"做了什么"以便反向执行；备忘录记录"当时是什么"以便恢复。两者常一起用于撤销栈。
- `pattern.gof.creational.prototype` — 原型复制一个已有实例作为新实例；备忘录保存旧状态用于回滚，意图不同。

## 测试说明

- 断言恢复后对象的可观察状态与快照时刻一致（用相等性或黄金输出）
- 断言快照对调用方不透明：外部只能存、不能改内部字段（靠类型设计保证）
- 测试连续快照与逆序恢复的组合
- 测试快照大小或耗时在可接受范围内（性能回归）

## 实现注意

- 备忘录 = 快照；不要在备忘录里放"撤销逻辑"，那是命令的职责
- 快照的内存占用与状态大小成正比，频繁快照要评估
- Rust 中快照结构体应保持 `Clone + Send`（若需跨线程）
- 需要持久化时用带版本号的序列化格式，不要直接序列化内存布局
