# 字典树（Trie (Prefix Tree)）

- 资产 ID：`algorithm.string.trie`
- 类型：`algorithm`（算法）
- 分类：`string`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`trie`、`字典树`、`前缀树`、`prefix tree`

## 一句话定位

沿字符逐层向下走，把前缀相同的键共享同一条路径，从而快速列出所有以某前缀开头的键。

输入框的自动补全、命令面板的模糊匹配、敏感词过滤，都要求"列出所有以 X 开头的候选"。

## 典型源文件形状

```rust
pub struct Trie {
    children: HashMap<char, Trie>,
    terminal: bool,          // 是否有一个键在此结束
    value: Option<String>,   // 键关联的值
}

impl Trie {
    pub fn insert(&mut self, key: &str, value: &str) {
        let mut node = self;
        for ch in key.chars() {
            node = node.children.entry(ch).or_default();
        }
        node.terminal = true;
        node.value = Some(value.to_owned());
    }
}
```

## 适用条件

- 需要前缀查询或自动补全
- 键共享较长公共前缀（文件路径、命令名、标识符）
- 需要按前缀做范围遍历（有序遍历字典树即字典序）
- 键集合较大且查找频繁

## 反例

- 只需要精确查找——哈希表更省内存
- 键数量少——线性扫描或有序表即可
- 键很长且前缀分散——每字符一节点会浪费空间
- 需要模糊匹配（允许编辑距离）——字典树只能做前缀匹配

## 并发风险

- 字典树的插入会修改节点，共享的字典树需要同步；只读查找可安全并发
- 常见做法是构建期独占、运行期只读（`Arc<Trie>`），这是最省锁的形态
- 若需要运行期动态插入，用 `RwLock` 分节点加锁或用分片字典树
- 内存消耗大时要用压缩字典树（Radix Tree）减少节点数

## 替代方案

- `algorithm.string.aho_corasick` — 需要同时匹配多个模式串时用 Aho-Corasick（本质是带失败指针的字典树）。
- `algorithm.datastructure.hash_table` — 只需要精确查找时用哈希表。

## 测试说明

- 插入后精确查找能命中，且键关联的值正确
- 前缀查询返回全部且仅有匹配的键
- 空键、前缀等于整键、前缀是整键的真前缀
- 删除后查询不到（若实现删除）
- 非 ASCII 键（按 char 而非 byte 存储）
- 大量键（十万级）下的查找与前缀查询性能

## 实现注意

- 优先标准库/成熟库：Rust 没有内置 trie，成熟 crate 有 `trie-rs`、`fst`（后者是压缩的有限状态机，更省内存），引入前需核查许可
- 复杂度：查找/插入 O(len)；空间 O(总字符数 × 每节点分支数)
- 稳定性：不适用
- 内存：每节点一个哈希表开销很大，是 trie 的主要成本；压缩 trie 或 `fst` 更省
- 溢出：深度递归的实现要注意栈深（长键），用迭代更安全
- 极端输入：超长键、十万级键、单字符键、空键、含非 ASCII 的键
- 并发安全：只读共享安全；动态插入需要同步或分片
- 限制：内存开销大；不支持模糊匹配；不能直接做范围查询以外的复杂查询
