# 六边形架构（Hexagonal Architecture）

- 资产 ID：`pattern.arch.hexagonal_architecture`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`HexagonalArchitecture`、`六边形架构`、`ports and adapters`、`端口与适配器`

## 一句话定位

核心只定义"我要什么"（端口），外围实现"怎么做"（适配器），从而把框架、数据库、协议都关在门外。

把业务逻辑写进框架的回调里之后，升级框架就等于重写业务；六边形要求业务先独立存在。

## 典型源文件形状

```rust
// 端口：由核心定义，方向朝内
pub trait OrderStore {
    fn put(&self, o: &Order) -> Result<(), StoreError>;
}

pub trait PaymentGateway {
    fn charge(&self, amount: f64) -> Result<Receipt, PayError>;
}

pub struct CheckoutService {
    store: Box<dyn OrderStore>,
    pay: Box<dyn PaymentGateway>,
}
```

## 适用条件

- 同一核心需要对接多种外部技术（多种数据库、多个消息队列）
- 希望核心逻辑可以在没有外部依赖的情况下测试
- 需要替换或模拟外部系统（如支付沙箱）
- 长期维护、基础设施会持续演进的系统
- 系统边界：端口与适配器之间的边界就是"技术细节"与"业务规则"的分界：边界之外的界面、存储、协议实现可任意替换，边界之内不允许出现框架类型与第三方 SDK 类型。

## 反例

- 外部依赖只有一种且稳定——直接调用更简洁
- 端口与适配器数量差不多、转换逻辑很重——此时这层抽象是纯成本
- 把端口粒度切得太细（每个方法一个端口）——会得到接口碎片化
- 核心里其实没有业务逻辑（只是转发）——六边形就变成了"围绕一个空心的六边形"

## 并发风险

- 适配器实现要声明线程安全：核心通常被多线程调用，端口 trait 常需要 `Send + Sync`
- 端口的返回类型优先用不可变数据或值，避免把外部可变状态引入核心
- 入站适配器（HTTP handler、CLI）通常是每请求一个实例，因此内部可变状态用局部变量即可
- 出站适配器（连接池、消息客户端）通常是长生命周期共享对象，其线程安全由适配器负责
- 核心不应自行开启线程或持有全局状态，否则适配器的替换就不再彻底

## 替代方案

- `pattern.arch.clean_architecture` — 两者理念一致；整洁架构按层次组织，六边形按端口/适配器组织，实践中常合并使用。
- `pattern.arch.dependency_injection` — 依赖注入是把适配器装进端口的手段，六边形是端口划分的架构风格。

## 测试说明

- 核心测试：只用内存适配器（fake store、fake gateway）验证业务规则
- 适配器契约测试：每个适配器跑同一套端口契约测试，保证可替换性
- 端到端测试：用真实适配器验证集成路径
- 断言核心 crate 的依赖里没有出现数据库/HTTP/框架依赖（依赖方向检查）

## 实现注意

- 设计书明确：六边形架构属于现代工程模式，不在 GoF 23 之列
- "端口由核心拥有"是六边形的关键：如果端口定义在外层，依赖方向就反了
- 不要为每个函数都建端口；端口应按"外部系统/外部角色"划分
- Rust 中端口通常是 trait，适配器是实现 trait 的类型，用泛型或 `dyn` 按需选择
