# 隔离舱（Bulkhead）

- 资产 ID：`pattern.resilience.bulkhead`
- 类型：`pattern`（设计模式）
- 分类：`resilience`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Bulkhead`、`隔离舱`、`bulkhead pattern`、`舱壁隔离`

## 一句话定位

像船舱隔板一样把资源切开：每个舱有自己的配额，一个舱进水不会让整船沉。

一个租户的大批量导入占满了所有数据库连接，其它租户的正常请求全部超时。

## 典型源文件形状

```rust
pub struct Bulkheads {
    normal: Semaphore,   // 正常流量的配额
    bulk: Semaphore,     // 批量/导出等重操作的配额
}

impl Bulkheads {
    pub fn enter(&self, kind: TrafficKind) -> Result<Permit, Overloaded> {
        match kind {
            TrafficKind::Bulk => self.bulk.try_acquire(),
            TrafficKind::Normal => self.normal.acquire(),
        }
    }
}
```

## 适用条件

- 不同调用方或不同业务的重要性差异明显（在线请求 vs 批量导出）
- 存在被单一租户或单一任务耗尽共享资源的风险
- 下游资源有硬上限（连接池、线程数、内存配额）
- 希望"降级一部分"而不是"整体不可用"
- 系统边界：配额的作用范围限于本进程内的资源（线程、连接、内存）；跨进程共享的同一资源还需要数据库或网关层的限额。

## 反例

- 资源余量充足、负载均衡——隔离带来的只是配置负担
- 分区数量远大于资源量——每个分区都拿不到足够资源，反而全部变慢
- 隔离维度选错（按错误维度切分）——真正的风险路径没有被隔离
- 应用层隔离无法阻止底层共享资源（同一数据库实例）被打满——还需数据库层限额

## 并发风险

- 隔离的本质是"限额"，必须作用在真正受限的资源上（信号量、连接池、令牌）
- 使用信号量时要注意公平性：默认信号量对等待者不保证 FIFO，可能造成饥饿
- 分区应包含"预留额度"，避免所有分区同时占满时重要流量也被拒
- 嵌套获取多个分区配额时要固定顺序，否则可能死锁
- 限流器与隔离舱都拒绝请求时，要能区分错误原因（配额不足 vs 下游故障）

## 替代方案

- `pattern.resilience.circuit_breaker` — 断路器按"下游健康度"切断调用，隔离舱按"调用方优先级"分配配额，两者互补。
- `pattern.resilience.rate_limiter` — 限流限制的是速率，隔离限制的是并发占用；前者防滥用，后者防拖垮。

## 测试说明

- 配额测试：耗尽一个分区的配额后，断言其它分区仍能正常通过
- 拒绝路径测试：断言被拒绝的请求得到明确错误（可区分的 overload 错误）
- 释放测试：请求完成后配额被正确归还（无泄漏）
- 并发测试：多线程争抢配额，断言不超过上限且无饥饿
- 预留额度测试：断言预留部分不会被普通流量占用

## 实现注意

- 隔离舱常被称为"舱壁"（bulkhead），在云原生里也对应 cell 架构思路
- 隔离维度要按"故障传播路径"划分：按租户、按功能、按环境
- 隔离与限流不同：限流防滥用与过载，隔离防故障扩散
- 被隔离拒绝的请求应可观测，否则会变成"神秘失败"
