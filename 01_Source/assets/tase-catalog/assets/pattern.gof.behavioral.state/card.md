# 状态（State）

- 资产 ID：`pattern.gof.behavioral.state`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`State`、`状态模式`、`state pattern`

## 一句话定位

让"当前处于什么状态"决定"能做什么"，把状态相关的行为放进各自的状态对象里，消除巨型条件分支。

一个订单只有"待支付/已支付/已发货/已取消"四个状态，但代码里到处是 `if status == ...`，新增状态要改十几处分支。

## 典型源文件形状

```rust
pub enum OrderState {
    Pending(PendingOrder),
    Paid(PaidOrder),
    Shipped(ShippedOrder),
}

impl OrderState {
    pub fn ship(self) -> Result<OrderState, OrderError> {
        match self {
            OrderState::Paid(p) => Ok(OrderState::Shipped(ShippedOrder::new(p))),
            other => Err(OrderError::IllegalTransition(other)),
        }
    }
}
```

## 适用条件

- 对象的状态明显、状态相关的行为差异大
- 状态转换规则复杂或有非法转换需要显式拒绝
- 状态数量会持续增加，需要可维护的转换表
- 对象在生命周期内身份不变，但行为随状态改变

## 反例

- 状态少且转换简单——`enum` + `match` 更短，编译器还能帮你检查穷尽性
- 状态之间共享大量行为——抽象基类会变成一堆默认实现
- 状态只在启动时确定、之后不变——那就是一个配置，不是状态机
- 状态需要持久化并在重启后恢复——要考虑序列化格式与版本兼容

## 并发风险

- 状态转换是典型的并发争用点：应把"读取当前状态 + 执行转换"放在同一个临界区，避免 TOCTOU
- 用 `Mutex<State>` 保护状态机时，转换方法应接收锁而不是自行加锁，避免死锁
- 状态对象若持有资源（文件、连接），转换时要明确资源交接顺序，不能出现两个状态同时持有同一资源
- 状态机的非法转换应返回错误，而不是 panic：并发下非法转换是正常现象

## 替代方案

- `pattern.gof.behavioral.strategy` — 策略替换的是算法且状态不变；状态模式下行为随状态变化且状态本身携带数据。
- `pattern.gof.behavioral.command` — 命令封装请求以便排队与撤销；状态模式封装"当前处于什么"以便合法转换。

## 测试说明

- 用转换表驱动测试：枚举所有 (状态, 事件) 组合，断言结果状态与错误
- 断言非法转换返回错误而不是 panic 或静默忽略
- 断言状态携带的数据在转换中正确传递（如已付金额、预付款）
- 并发测试：多线程同时触发转换，断言最终状态与计数满足不变量（如金额不重复扣减）

## 实现注意

- Rust 用枚举表示状态机是首选：模式匹配穷尽性检查能挡住漏处理的转换
- 若状态过多且转换表密集，把转换表写成数据（表驱动）比写几十个分支更好维护
- 状态对象不应变成"什么都干"的对象；每个状态只负责该状态下的行为
- 状态机与持久化结合时，要定义状态与外部数据的一致性策略
