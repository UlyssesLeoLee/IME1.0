# 指数退避与抖动（Exponential Backoff with Jitter）

- 资产 ID：`algorithm.concurrency.exponential_backoff_jitter`
- 类型：`algorithm`（算法）
- 分类：`concurrency`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`exponential_backoff_jitter`、`指数退避抖动`、`backoff jitter`、`退避算法`

## 一句话定位

第 n 次重试前等待 base·2^n 并取随机抖动，用等待把并发重试错开，避免惊群。

服务恢复的瞬间，所有客户端同时重试，瞬间流量是平时的十倍，把刚恢复的服务再次打垮。

## 典型源文件形状

```rust
pub fn backoff(base_ms: u64, cap_ms: u64, attempt: u32) -> u64 {
    let exp = base_ms.saturating_mul(1u64 << attempt.min(20));
    let exp = exp.min(cap_ms);
    // full jitter：在 [exp/2, exp] 之间随机，避免太早重试
    exp / 2 + rand::random::<u64>() % (exp - exp / 2 + 1)
}
```

## 适用条件

- 对瞬时故障（网络抖动、限流、实例重启）做重试
- 多个客户端会同时遇到同一故障（惊群风险高）
- 调用可幂等或带幂等键
- 失败原因可区分"可重试"与"不可重试"

## 反例

- 错误是确定性的——重试只会浪费时间
- 操作不可逆且无幂等键——重试会造成重复副作用
- 用户正在等待交互结果——应快速失败并提示稍后重试
- 服务已被熔断——重试会绕过保护

## 并发风险

- 退避等待必须可被取消：调用方超时或取消时，正在等待的线程应立即结束
- 所有客户端使用相同种子会导致同步重试——随机源应来自不可预测的熵
- 重试会放大并发量：必须与信号量/隔离舱配合限制在途请求总数
- 等待期间应释放锁，不要持锁退避
- 退避状态（当前尝试次数）应按调用或按目标区分，避免一个目标的失败拖慢其它目标

## 替代方案

- `pattern.resilience.retry_with_exponential_backoff_and_jitter` — 现代工程模式卡描述的是完整的重试策略（含可重试错误分类与总超时），本卡专注退避算法本身。
- `algorithm.concurrency.token_bucket` — 令牌桶限制的是请求速率，可与退避配合控制重试流量。

## 测试说明

- 用注入的时钟与随机源做确定性测试：断言等待时长落在 [exp/2, exp] 区间内
- 断言等待时长随尝试次数指数增长且不超过上限
- 断言尝试次数达到上限后停止
- 断言取消后不再继续等待
- 统计测试：大量并发调用时，等待时刻不应高度重合（削峰效果）
- 断言总等待时间不超过总超时预算

## 实现注意

- 优先标准库/成熟库：退避逻辑通常自写（约 10 行）；随机源用 `rand` crate（MIT/Apache-2.0），引入前需核查许可
- 复杂度：时间随尝试次数指数增长（受上限约束），空间 O(1)
- 稳定性：不适用
- 内存：常数
- 溢出：`1u64 << attempt` 在 attempt 很大时会溢出——必须先 clamp 或用 saturating_mul
- 极端输入：尝试次数很大、退避上限很大、总超时很小（此时可能一次都等不到）
- 并发安全：纯计算；共享的重试计数器需要同步（通常按调用局部保存即可）
- 限制：只处理时间维度的退避；不解决"该不该重试"的判定，也不解决并发量放大
