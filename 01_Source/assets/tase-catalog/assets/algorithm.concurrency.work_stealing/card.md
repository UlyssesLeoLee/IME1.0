# 工作窃取（Work Stealing）

- 资产 ID：`algorithm.concurrency.work_stealing`
- 类型：`algorithm`（算法）
- 分类：`concurrency`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`work_stealing`、`工作窃取`、`work stealing scheduler`、`窃取调度`

## 一句话定位

每个线程一个双端队列：自己从头部取任务，偷别人时从尾部取，两端分离让竞争极小。

共享一个任务队列时，所有线程都争抢同一把锁，线程越多竞争越激烈，扩展性反而下降。

## 典型源文件形状

```rust
// 每个 worker 一个双端队列（deque）
//   本地取任务：从头部 pop（LIFO，缓存友好）
//   窃取任务：从尾部 steal（FIFO，偷到的任务通常更老、可能更大）

pub struct Worker {
    deque: Mutex<VecDeque<Task>>,
    rng: RandomState,          // 用于随机选择窃取目标
}

impl Worker {
    pub fn find_task(&self, others: &[Worker]) -> Option<Task> {
        if let Some(t) = self.deque.lock().unwrap().pop_front() { return Some(t); }
        // 随机挑一个其他 worker，从尾部窃取
        others.iter().filter(|o| !std::ptr::eq(o, self)).find_map(|o| o.deque.lock().unwrap().pop_back())
    }
}
```

## 适用条件

- 任务数量多且粒度适中，任务间依赖少
- 需要自适应负载均衡（任务耗时不均）
- 要避免共享队列的锁竞争
- 运行时（语言或库）级别的任务调度器

## 反例

- 任务数量少（少于线程数）——静态分配即可
- 任务粒度极细（几纳秒）——调度开销超过收益
- 任务之间有严格顺序或强依赖——需要专门的依赖调度
- 任务数固定且可预估——分块调度更简单

## 并发风险

- 双端队列的两端分离是降低竞争的关键：本地操作与窃取操作作用于不同的同步域
- 窃取时随机选择目标（而不是按顺序），避免所有空闲线程同时抢同一个队列
- 窃取失败（目标队列为空）应短暂退避（自旋 + 让出），否则会空转烧 CPU
- 任务粒度过细会导致调度开销主导；过粗则负载不均
- 嵌套并行（任务里再开并行）要限制深度，否则线程数爆炸
- 窃取到的任务可能与本地任务有数据竞争——共享状态的同步责任仍在使用者
- 实现上要处理"队列为空但线程不能退出"的竞态：通常用"睡眠/挂起 + 唤醒"协议

## 替代方案

- `algorithm.concurrency.bounded_queue` — 有界队列是单个共享缓冲，工作窃取是每线程一个队列并相互偷取。
- `pattern.concurrent.actor` — actor 强调"消息投递到状态拥有者"，工作窃取是任务调度策略，两者常在同一运行时中共存。

## 测试说明

- 断言所有任务被执行且恰好一次（用计数器校验）
- 断言不均衡的任务分布下总时间明显优于静态分配
- 断言线程在任务耗尽后能正确退出（不死锁、不空转）
- 断言窃取不会破坏任务的顺序约束（若调度器承诺了这一点）
- 压力测试：大量短任务、少量长任务
- 并发测试：TSAN 下无数据竞争

## 实现注意

- 优先标准库/成熟库：Rust 标准库没有工作窃取调度器；成熟实现有 Rayon（MIT/Apache-2.0）与 Tokio 的多线程运行时，引入前需核查许可
- 复杂度：入队/出队/窃取均为 O(1) 摊还，空间 O(任务总数)
- 稳定性：不适用
- 内存：每线程一个队列，队列总容量随任务数增长
- 溢出：任务计数与容量用 `usize`；线程数上限受系统限制
- 极端输入：单任务、千万级短任务、任务耗时不均、频繁的窃取失败
- 并发安全：调度器本身是并发原语；共享业务数据仍需用户同步
- 限制：需要运行时支持；不适合强顺序依赖任务；嵌套并行需限制深度
