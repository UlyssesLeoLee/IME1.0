# 快速排序（Quicksort）

- 资产 ID：`algorithm.sorting.quick_sort`
- 类型：`algorithm`（算法）
- 分类：`sorting`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`quick_sort`、`快速排序`、`quicksort`

## 一句话定位

原地、平均最快的经典比较排序：随机选枢轴分区，一半放左一半放右，再递归处理两侧。

需要一个常数小、缓存友好、无需额外内存的通用排序，同时要避免"已排序输入退化成 O(n²)"的经典陷阱。

## 典型源文件形状

```text
quick_sort(a, lo, hi):
    if lo >= hi: return
    p = partition(a, lo, hi)          // 枢轴归位
    quick_sort(a, lo, p-1)
    quick_sort(a, p+1, hi)

partition(a, lo, hi):               // Lomuto 分区
    pivot = a[random(lo..=hi)]
    swap(a[hi], pivot)
    store = lo
    for k = lo..hi:
        if a[k] < a[hi]: swap(a[k], a[store]); store++
    swap(a[store], a[hi])
    return store
```

## 适用条件

- 通用内存内排序，追求平均性能与小的常数
- 数据可以原地重排（不需要额外 O(n) 缓冲）
- 比较成本是主要开销（元素本身搬运便宜）
- 能接受不稳定排序

## 反例

- 需要稳定排序——快速排序不满足
- 需要最坏情况 O(n log n) 保证且不能用随机枢轴时——改用归并或堆排序
- 数据量极大且内存紧张——堆排序更稳妥
- 外部排序（磁盘）——快排的随机访问代价高，应使用归并

## 并发风险

- 原地修改数组，不是共享数据上的并发安全操作
- 分区后的左右两段互不依赖，理论上可并行排序（但需要额外复制或复杂同步）
- 并行快排在实践中常不如"分块并行 + 归并"
- 递归深度在最坏情况可达 O(n)，可能导致栈溢出——生产实现应用显式栈或小数组切换插入排序

## 替代方案

- `algorithm.sorting.merge_sort` — 需要稳定性或最坏情况保证时用归并。
- `algorithm.sorting.heap_sort` — 需要 O(1) 额外空间时用堆排序。

## 测试说明

- 与标准库排序交叉比较，断言排列一致
- 专门测对抗输入：已排序、逆序、全部相等、管道输入（organ pipe）
- 多次运行随机枢轴版本，断言结果始终正确（随机性不能影响正确性）
- 空数组、单元素、两个元素
- 栈深度测试：对超大已排序数组断言不栈溢出（用显式栈实现验证）
- 性能回归：断言平均耗时在预期上限内

## 实现注意

- 优先标准库：Rust 的 `slice::sort_unstable` 是经过对抗输入测试的 pdqsort，不要在生产中手写快排
- 复杂度：平均 O(n log n)，最坏 O(n²)（枢轴极端不平衡时），额外空间 O(log n) 递归栈（可改为迭代 + 显式栈）
- 稳定性：不稳定
- 内存：原地（O(log n) 栈），枢轴随机化可避免最坏情况
- 溢出：分区下标计算注意 `usize` 溢出；随机数生成要无偏（`rand` 的 `gen_range`）
- 极端输入：大量重复元素时三路分区（<, ==, >）能显著减少递归深度
- 并发安全：原地修改，单线程独占；并行化需额外机制且收益有限
- 限制：递归深度风险、比较次数不稳定、不稳定
