# 旁路缓存（Cache-Aside）

- 资产 ID：`pattern.integration.cache_aside`
- 类型：`pattern`（设计模式）
- 分类：`integration`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`CacheAside`、`旁路缓存`、`cache aside`、`缓存旁路`

## 一句话定位

把缓存当成一个"可随时丢掉、可重建"的加速层，由应用代码决定何时回填与失效。

热点数据每秒被查上万次，每次都打数据库会拖垮库；但又不能把数据长期焊死在进程里。

## 典型源文件形状

```rust
pub fn get_profile(cache: &mut Cache, db: &Db, id: u64) -> Result<Profile, Error> {
    if let Some(p) = cache.get(&key(id)) { return Ok(p); }
    let p = db.load_profile(id)?;
    cache.set(&key(id), &p, Duration::from_secs(300));
    Ok(p)
}

// 写路径：先写源，再失效缓存
pub fn update_profile(db: &mut Db, cache: &mut Cache, p: &Profile) -> Result<(), Error> {
    db.save_profile(p)?;
    cache.del(&key(p.id));
    Ok(())
}
```

## 适用条件

- 读远多于写，且存在热点数据
- 源数据读取成本明显高于缓存读取
- 可以接受短暂的数据陈旧
- 缓存可丢失并从源数据重建
- 系统边界：缓存的读写时机在边界内，缓存内容的正确性与源数据的真值在边界外——源数据才是真相；跨副本的失效广播需要额外的通道。

## 反例

- 数据量小、读取本来就快——缓存的失效逻辑会成为纯负担
- 需要强一致读——请改用源数据加锁或直接读源
- 缓存无法重建（计算代价极高且不可再计算）——不适合旁路缓存
- 写远多于读——缓存命中率极低，内存与一致性成本白付

## 并发风险

- 缓存击穿：热点键过期瞬间大量请求同时回源——用互斥回填、逻辑过期或单飞（single-flight）
- 缓存雪崩：大量键同时过期导致源被打垮——给 TTL 加随机抖动
- 缓存穿透：查询不存在的键，每次都回源——对"空结果"也做短 TTL 缓存或布隆过滤器
- 多副本部署时各进程有独立本地缓存，失效广播要靠消息通知，不能只清本机
- 缓存客户端本身的连接与超时参数必须设好，否则缓存故障会拖垮源数据
- 回填与更新竞态：回源读到的旧值可能在更新之后写回缓存——用版本号或先删后写缓解

## 替代方案

- `pattern.integration.read_copy_update` — 旁路缓存放在应用进程内；读副本更新把数据复制到独立查询库，适合更重的查询负载。
- `pattern.arch.cqrs` — CQRS 的读侧本身常配合缓存使用；两者是不同层面的关注点。

## 测试说明

- 命中测试：断言缓存命中时不触碰源数据（用计数假实现）
- 回填测试：断言未命中后数据被写入缓存且下次命中
- 失效测试：更新源数据后断言缓存被清理（这是最容易漏的一条）
- 并发击穿测试：多线程同时请求同一过期键，断言源只被访问一次或次数受控
- 故障测试：缓存不可用时断言系统降级到源数据而不是整体失败

## 实现注意

- 缓存是加速层不是真相来源；缓存丢失后系统必须能自愈
- TTL 要按数据更新频率与业务容忍度设定，配合随机抖动防雪崩
- 删除缓存与更新源数据的顺序：常见做法是"更新源 → 删除缓存"，反序会有一致性漏洞
- 缓存 key 要包含所有影响结果的维度（版本、语言、租户）
