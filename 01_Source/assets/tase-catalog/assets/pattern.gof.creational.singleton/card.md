# 单例（Singleton）

- 资产 ID：`pattern.gof.creational.singleton`
- 类型：`pattern`（设计模式）
- 分类：`creational`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Singleton`、`单例模式`、`单例`

## 一句话定位

把"唯一实例"的约束放到类型自身上，用一次线程安全的初始化换来全局可达性。

配置、连接池、缓存这类"全进程只应有一份"的资源，如果到处传递引用会把调用签名撑爆，而随手用 `static mut` 又会引入数据竞争。

## 典型源文件形状

```rust
use std::sync::OnceLock;

pub struct Config { pub endpoint: String }

static CONFIG: OnceLock<Config> = OnceLock::new();

impl Config {
    pub fn global() -> &'static Config {
        CONFIG.get_or_init(|| Config {
            endpoint: "https://example.invalid".to_owned(),
        })
    }
}
```

## 适用条件

- 资源昂贵且必须全进程唯一（连接池、加密上下文、进程级缓存）
- 确实没有自然的拥有者来传递该对象（无应用框架、无依赖注入容器的独立工具）
- 需要一个稳定的全局句柄供回调、信号处理等无处注入的场景使用
- 单例的只读配置在初始化后不再变化

## 反例

- 测试需要替换或打桩该对象——单例会污染测试间状态，应改为依赖注入
- 对象需要按请求、按租户、按配置切换——进程级单例粒度错误
- 业务中出现了"单例里再存一堆可变业务状态"——那是隐藏的全局变量，不是单例的正当用途
- 并发初始化很难写对——如果一份内存里的状态真的需要被多线程共享，先考虑换成消息传递

## 并发风险

- 并发初始化是单例的头号风险：裸 `static mut` + 惰性初始化会产生数据竞争，必须用 `OnceLock`/`LazyLock`（Rust 1.70+）或 `std::sync::Once`
- `OnceLock::get_or_init` 在初始化函数panic 时不会重试；初始化函数应尽量不 panic，把错误通过 `get_or_try_init` 返回
- 全局可变状态是第二风险：`static mut` 引用在多线程下是 UB，必须用 `Mutex`/`RwLock`/`Atomic*` 包装可变部分
- 持锁访问单例时要注意锁顺序，避免与其它全局锁形成环路死锁；不要在持锁期间回调外部代码
- 单例的析构顺序不保证：不要在单例的 `Drop` 里依赖其它单例仍然存活
- 进程内唯一不等于线程安全：`&Config` 的共享读取安全，但任何内部可变状态都要单独同步

## 替代方案

- `pattern.arch.dependency_injection` — 绝大多数"我需要一个全局对象"的需求，正确解法是把依赖显式注入到使用方，测试与并发都更安全。
- `pattern.gof.structural.proxy` — 当真正的问题是"隐藏昂贵对象、只暴露一个轻量入口"时，代理比单例更贴切且没有全局状态。

## 测试说明

- 并发初始化测试：多线程同时首次访问 `global()`，断言只初始化一次且返回同一地址
- 断言初始化函数只被调用一次（用计数器或注入的构造钩子）
- 对含可变状态的单例做并发读写压力测试（TSAN 或 Miri 可捕获竞争）
- 测试单例在不同测试用例之间的状态残留——若残留导致用例互相影响，说明它不该是单例
- 断言进程退出时的析构行为不会 panic

## 实现注意

- Rust 优先 `OnceLock`/`LazyLock`/`OnceCell`，不要手写 `static mut` 单例
- 单例是"进程内唯一"；多进程部署时每进程各一份，不要假设它是"全局唯一"
- 如果只是需要避免重复计算，用 `OnceLock` 包住结果即可，不必设计成"单例类"
- 设计书明确要求：本目录的资产只是知识卡，单例的认证实现必须单独走测试/许可/签名流程
