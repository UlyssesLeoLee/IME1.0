# 依赖注入（Dependency Injection）

- 资产 ID：`pattern.arch.dependency_injection`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`DependencyInjection`、`依赖注入`、`DI`、`dependency injection`

## 一句话定位

让使用方声明"我需要什么"，由外部决定"给我什么"，从而把实现选择、生命周期与测试替身都挪到组装点。

业务类里直接 `SqlClient::connect(...)`，测试时无法替换、集成测试会真的连库；改一个实现还要改所有调用点。

## 典型源文件形状

```rust
pub trait UserStore: Send + Sync {
    fn find(&self, id: u64) -> Result<Option<User>, StoreError>;
}

pub struct UserService<S: UserStore> { store: S }

impl<S: UserStore> UserService<S> {
    pub fn new(store: S) -> Self { Self { store } }
}
```

## 适用条件

- 业务逻辑需要依赖外部资源（数据库、HTTP、文件、时钟）
- 依赖需要在测试中替换（假实现、内存实现）
- 同一业务逻辑需要绑定不同实现（多租户、多后端）
- 希望依赖关系在组装点一目了然，而不是散落在各处 new
- 系统边界：只覆盖"对象如何获得依赖"这一步，不规定依赖从哪来、生命周期由谁管理；容器、服务定位器与手工装配都不在模式的边界内。

## 反例

- 依赖只是纯函数或值对象——直接传参即可，DI 只是换了个说法
- 注入层级太深（use case 依赖 service，service 依赖 5 个仓储）——那是过度设计，应先简化领域模型
- 用容器做全局服务定位（随处 `container.get()`）——那是隐藏的全局依赖，DI 的收益被抵消
- 注入的是具体实现而非抽象——那么只是把构造搬了家，没有换来可替换性

## 并发风险

- 注入的依赖若被多线程共享，其 `Send`/`Sync` 能力必须显式声明（trait 约束），否则编译期会发现问题
- 注入长生命周期的连接池时，生命周期由谁负责要明确：容器、调用方还是依赖自身
- 把 `&mut self` 的可变依赖注入到需要并发调用的对象里，会迫使调用方加锁；优先注入不可变或内部同步的依赖
- 测试替身（fake）常带内部状态，跨线程共享时要同步；断言替身被调用时也要考虑并发下的计数原子性

## 替代方案

- `pattern.gof.creational.singleton` — 单例是"全局可达"，依赖注入是"显式可达"；新代码应优先依赖注入。
- `pattern.arch.hexagonal_architecture` — 六边形架构是依赖注入在架构层面的应用：端口与适配器的边界即注入点。

## 测试说明

- 为每个业务用例写单元测试，注入假实现，断言行为而不触碰真实外部资源
- 断言注入的依赖确实被使用（假实现记录调用），避免"注入了却没用"的静默失效
- 测试装配代码：确保生产装配把正确的实现绑到正确的端口上
- 在集成测试中把假实现换成真实实现跑同一套用例，验证契约一致

## 实现注意

- 设计书明确：现代工程模式并不全部属于 GoF 23 模式，依赖注入不属于 GoF
- DI 的收益来自"可替换 + 可测试"，不是为了"少写 new"
- Rust 里没有反射式容器，手工装配（构造函数的组合）往往比容器更清晰、更易读
- 用 trait 表达端口时注意对象安全；泛型版本保留静态派发但会扩大编译产物体积
