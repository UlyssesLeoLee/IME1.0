# 组合（Composite）

- 资产 ID：`pattern.gof.structural.composite`
- 类型：`pattern`（设计模式）
- 分类：`structural`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Composite`、`组合模式`、`composite pattern`

## 一句话定位

让"单个对象"和"一组对象"对调用方是同一种东西，从而可以在任意深度上递归地统一处理。

文件系统的目录与文件、UI 的容器与控件、AST 的节点与子树——如果每个调用点都写 `if is_group { ... } else { ... }`，代码会被类型判断淹没。

## 典型源文件形状

```rust
pub enum Node {
    Leaf { size: u64 },
    Group { children: Vec<Node> },
}

impl Node {
    pub fn total_size(&self) -> u64 {
        match self {
            Node::Leaf { size } => *size,
            Node::Group { children } => children.iter().map(Node::total_size).sum(),
        }
    }
}
```

## 适用条件

- 数据天然是树形（目录、场景图、语法树、UI 树、组织结构）
- 调用方希望对整棵树做统一操作而不写类型分支
- 容器与叶子的操作集合高度重合
- 结构会递归嵌套，需要整体统计或整体变换

## 反例

- 结构是图而不是树（同一节点被多处引用）——会导致重复遍历与语义歧义
- 叶子与容器的操作差别很大——统一接口会退化成"到处 `match` 变体"
- 结构只有两层且不会加深——两层 `if` 就够了
- 需要频繁按路径查找/按 ID 更新——树形结构的随机访问代价高，应改用哈希表或扁平结构

## 并发风险

- 树通常由单线程构建、多线程只读：共享时应保证节点及其子节点不可变
- 若要在多线程下并发修改同一棵树，需要额外的锁或 copy-on-write；组合模式本身不提供并发保证
- 用 `Arc` 共享子树时，注意 `Arc` 计数是原子的但内容未必安全；可变内容仍需同步
- 递归遍历在深度很大时可能栈溢出，深树场景应改为显式栈或改用迭代器组合

## 替代方案

- `pattern.gof.structural.decorator` — 当意图是"给对象叠加行为"而不是"把对象组织成树"时用装饰。
- `pattern.gof.behavioral.iterator` — 当只需要顺序遍历而不需要统一操作接口时，迭代器 + 闭包往往比组合更轻。

## 测试说明

- 覆盖空组合、单叶子、单层嵌套、深层嵌套四类结构
- 对每个操作（求和、查找、渲染）用同一组用例分别跑在叶子和组合上，确认统一接口行为一致
- 断言组合的子元素顺序被保留（若语义要求有序）
- 对大深度结构做压力测试，确认不会栈溢出

## 实现注意

- Rust 中枚举 + `match` 往往比 trait 对象更贴切：可穷尽检查、无动态派发、无 `Box` 开销
- 若必须用 trait 实现统一接口，注意对象安全；叶子与容器实现同一 trait 时避免泛型方法
- 组合模式常与访问者（Visitor）搭配：结构稳定而操作多变时用访问者
- 不要让组合节点同时承担"数据"与"业务规则"，否则树的每一层都变成业务耦合点
