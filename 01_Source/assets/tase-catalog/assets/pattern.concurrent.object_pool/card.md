# 对象池（Object Pool）

- 资产 ID：`pattern.concurrent.object_pool`
- 类型：`pattern`（设计模式）
- 分类：`concurrent`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`ObjectPool`、`对象池`、`object pool`、`连接池`

## 一句话定位

把"新建对象"换成"借一个现成的"，用上限换取可控的内存与资源占用。

每次请求都新建数据库连接或大缓冲区，高峰期会耗尽文件句柄；连接池让请求复用有限连接。

## 典型源文件形状

```rust
pub struct Pool<T> {
    inner: Mutex<Vec<T>>,      // 空闲对象
    factory: Box<dyn Fn() -> T + Send + Sync>,
    capacity: usize,
}

impl<T> Pool<T> {
    pub fn get(&self) -> PooledGuard<T> { /* 取空闲对象或新建；归还时放回 */ }
}
```

## 适用条件

- 对象构造代价高（建立连接、分配大缓冲区、加载资源）
- 对象数量受硬性资源上限约束（连接数、文件句柄、显存）
- 对象是可复用的且没有跨次使用必须重置的状态
- 流量有明显峰值，复用能显著降低延迟抖动
- 系统边界：池只管理被池化对象的获取、归还与数量上限，不管理对象所连接的后端资源（连接失效、服务端状态）——那属于被池化对象自身的职责。

## 反例

- 对象构造廉价——池化收益不抵管理成本
- 对象带请求相关状态（未清理）——复用会串数据，必须有明确的 reset 语义
- 池大小无法估算——太小会降低吞吐，太大会耗尽资源
- 进程内多池竞争同一底层资源（如都开数据库连接）——总连接数仍然失控

## 并发风险

- 取用与归还是原子的：用 `Mutex<Vec<T>>` 或无锁栈，避免"取到同一个对象两次"
- 归还必须可靠：Rust 中用 `Drop` 实现守卫（`PooledGuard`）保证异常路径也能归还
- 池满时的策略要显式：等待、扩容还是新建临时对象，行为不同
- 池中的对象在归还前必须完全重置（连接重置、缓冲区清零）
- 对象若持有句柄，池销毁时要全部释放，否则会泄漏（守卫析构顺序很关键）
- 池大小是资源上限的一部分，应与连接数、文件句柄限制一起规划

## 替代方案

- `pattern.gof.structural.flyweight` — 对象池复用"实例"，享元共享"不可变数据"；池不减少唯一实例数，享元减少对象数。
- `pattern.resilience.bulkhead` — 对象池的上限本身就是一种资源隔离，可与隔离舱配合。

## 测试说明

- 复用测试：借出再归还，断言拿到的是同一个实例且状态已被重置
- 上限测试：断言池内对象数不超过容量
- 并发测试：多线程同时借还，断言不会借到同一对象两次（TSAN 下无竞争）
- 异常路径测试：借出后 panic 或提前返回，断言对象仍被归还
- 销毁测试：池销毁后断言底层资源（连接/句柄）被释放

## 实现注意

- Rust 标准库没有通用对象池，成熟选择是 `crossbeam`/`bb_pool` 等；引入外部依赖需评估许可
- 连接池与普通对象池不同：连接有服务端状态，必须有健康检查与失效重建
- 归还时的重置逻辑是池化最容易出错的地方：残留状态会导致极难排查的串数据
- 池不是越大越好：池太大等于没有池化，还会在冷启动时集中占用资源
