# 原型（Prototype）

- 资产 ID：`pattern.gof.creational.prototype`
- 类型：`pattern`（设计模式）
- 分类：`creational`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Prototype`、`原型模式`、`clone pattern`

## 一句话定位

用"以现有对象为模板的复制"代替"从零构造"，在构造成本高或必须带着一整套合法初始状态时省事。

某种对象的初始化要解析一整套默认参数、预热缓存、建索引，重复做一遍代价高；而用"照着现成的那个再做一个"显然更快。

## 典型源文件形状

```rust
#[derive(Clone)]
pub struct ReportTemplate {
    pub title: String,
    pub sections: Vec<Section>,
    pub style: Rc<ReportStyle>,   // 共享的不可变部分
}

impl ReportTemplate {
    pub fn clone_with_title(&self, title: &str) -> Self {
        let mut copy = self.clone();
        copy.title = title.to_owned();
        copy
    }
}
```

## 适用条件

- 构造代价明显高于复制代价（大型模板、预编译正则、展开的索引）
- 需要基于一个"标准样本"产生同族实例（报表模板、文档骨架、默认配置）
- 调用方要能修改副本而不影响原型
- 系统中已存在大量同类实例，逐一重建代价不可接受

## 反例

- 对象构造就是几个字段赋值——复制没有意义
- 对象持有连接、文件句柄、线程等资源——克隆会制造重复句柄或悬垂引用
- 需要"精确拷贝"语义时，先确认是深拷贝还是浅拷贝，业务上说不清就不要引入原型
- 对象状态复杂到 clone 无法维护不变量时——改用显式的"复制构造"或重新构造

## 并发风险

- 浅拷贝会共享底层缓冲区：一个线程改副本会影响原型，必须用写时复制（`Rc::clone`/`Arc::clone`）或深拷贝隔离
- 原型本身若被多线程共享读取，克隆期间的读必须无锁，因此原型状态应视为不可变
- `Arc<T>` 的 `clone` 只复制引用计数，不复制数据；若需要独占的可变副本，需 `Arc::try_unwrap` 或改为深拷贝
- 克隆钩子里若分配内存或访问全局状态，会把并发问题带进看似"纯本地"的操作

## 替代方案

- `pattern.gof.creational.builder` — 当"复制"只是因为初始状态复杂而需要一个变体时，生成器往往比原型更好控制。
- `pattern.gof.creational.abstract_factory` — 当你要的是"切换产品族"而不是"复制现有实例"时用抽象工厂。

## 测试说明

- 断言克隆后的对象与原型"字段相等但身份不同"，并逐字段比较可变部分
- 断言修改副本不影响原型（这是原型模式的核心不变式）
- 对含引用计数的类型测试克隆/丢弃后的引用计数无泄漏（可借助 sanitizer 或 Miri）
- 对内部含集合的类型，断言集合是深拷贝还是浅拷贝符合文档声明

## 实现注意

- 原型在 Rust 中对应 `Clone`，但 `Clone` 语义由实现者决定，"浅拷贝"是常见陷阱
- 使用 `#[derive(Clone)]` 前要确认每个字段的克隆语义符合预期，尤其是 `Rc`/`Arc`/裸指针
- 用 `Cow` 表达"可能借用可能拥有"是原型在 Rust 中的更安全替代
- 不要把原型当作"省内存的通用手段"；它省的是构造时间，不是内存
