# 滑动窗口（Sliding Window）

- 资产 ID：`algorithm.searching.sliding_window`
- 类型：`algorithm`（算法）
- 分类：`searching`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`sliding_window`、`滑动窗口`、`滑窗`

## 一句话定位

维护一个随扫描移动的区间，进出各更新一次状态，让"所有子区间"的统计从 O(n²) 降到 O(n)。

求"最长无重复子串"、"和不超过 K 的最长子数组"，每个起点都重扫一遍是 O(n²)。

## 典型源文件形状

```rust
pub fn longest_unique(s: &[u8]) -> usize {
    let mut last = [usize::MAX; 256];
    let mut start = 0usize;
    let mut best = 0usize;
    for (i, &b) in s.iter().enumerate() {
        if last[b as usize] >= start { start = last[b as usize] + 1; }
        last[b as usize] = i;
        best = best.max(i - start + 1);
    }
    best
}
```

## 适用条件

- 问题只关心连续区间
- 窗口状态可以用"进入时加、离开时减"的方式增量维护
- 需要所有区间的最大值/最小值/可行性判定
- 数据可顺序扫描（流式也常可）

## 反例

- 关心的是任意子集而非连续区间——窗口不适用
- 窗口状态无法增量维护（如区间内最值不可加减）——改用单调队列或其它结构
- 区间长度受多种复杂约束——单调性难以证明
- 数据量小且区间数少——暴力更简单

## 并发风险

- 窗口状态是有序结构的增量更新，不适合并发共享；并行化应按分片 + 边界合并
- 分片并行时每个分片的窗口状态需要能合并（如前缀/后缀信息），否则无法并行
- 流式场景下窗口状态天然是单线程的；多线程读取同一流需要额外同步
- 共享的"最后出现位置"表若被多线程写入需同步，通常应保持每线程一份

## 替代方案

- `algorithm.searching.two_pointers` — 双指针是窗口的固定形态（两个指针相向），窗口是两个同向指针的推广。
- `algorithm.datastructure.monotonic_stack` — 窗口内需要维护单调结构（如窗口最大值）时，配合单调栈使用。

## 测试说明

- 与暴力枚举所有子区间（小规模）交叉比较，断言结果一致
- 空输入、单元素、全相同、全不同
- 窗口刚好等于数组长度、窗口无法收缩的极端情况
- 含非 ASCII 字节（若是字节算法）
- 断言窗口状态维护正确：与每次重算的状态对比

## 实现注意

- 优先标准库/成熟库：Rust 的 `slice::windows` 提供了窗口迭代器，但状态维护仍需手写
- 复杂度：时间 O(n) 均摊（每个元素进入与离开各一次），额外空间 O(k)（窗口大小）或 O(1)
- 稳定性：不适用
- 内存：状态表大小取决于字母表（字节用 256 项表）
- 溢出：长度与下标用 `usize`；`last[b] + 1` 在 `usize::MAX` 哨兵时要小心，用 `>=` 比较避免加法溢出
- 极端输入：空输入必须返回 0；窗口无法缩小时要保证不越界
- 并发安全：窗口状态通常不是并发安全的；并行化需要可合并的边界状态
- 限制：只适用于连续区间问题，且要求窗口状态可增量维护
