# 限流器（Rate Limiter）

- 资产 ID：`pattern.resilience.rate_limiter`
- 类型：`pattern`（设计模式）
- 分类：`resilience`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`RateLimiter`、`限流`、`rate limiting`、`throttling`

## 一句话定位

在入口处设一个闸门，按时间或配额放行请求，超出的部分要么快速拒绝、要么排队等待。

对外开放的 API 被脚本刷流量，重查询把数据库打满，所有正常用户一起受影响。

## 典型源文件形状

```rust
pub struct TokenBucket {
    capacity: u32,      // 桶容量（允许的突发量）
    refill_per_sec: u32,
    tokens: Mutex<u32>,
    last: Mutex<Instant>,
}

impl TokenBucket {
    pub fn try_acquire(&self, n: u32) -> bool { /* 补充令牌后判断是否足够 */ }
}
```

## 适用条件

- 接口对外部开放，需要保护自身与下游
- 存在突发流量（营销活动、批处理）需要平滑
- 需要按租户、API 或 IP 精细分配配额
- 过载时"快速失败并告知"比"排队到超时"更可取
- 系统边界：限流判定在本进程内完成时只约束单节点；跨节点的全局配额需要共享计数存储，超出单进程模式的边界。

## 反例

- 限流维度选错（按 IP 限流却按账号消费）——业务会直接受损
- 配额设得太紧导致正常业务被拒——限流器最常见的失败模式
- 需求是限制并发数而不是速率——用信号量/隔离舱
- 多节点部署却各节点独立限流——总流量仍可能超过下游承受力

## 并发风险

- 令牌桶的状态更新必须原子：先取锁判断再放行，否则并发下会超发
- 分布式限流需要共享计数存储（Redis 等），会引入网络延迟与存储可用性依赖
- 分布式限流要考虑时钟漂移与存储往返延迟，通常用"乐观扣减 + 失败即放行"
- 限流判定应在最靠前的位置，避免消耗资源后才被拒
- 拒绝与排队是两种策略：排队（`bounded_queue`）会占用连接与内存，突发大时要慎用
- 限流器的锁粒度要细：全局锁会让所有请求排队

## 替代方案

- `pattern.resilience.bulkhead` — 限流限制"速率"，隔离舱限制"并发占用"；两者经常一起使用（限速率 + 限并发）。
- `algorithm.concurrency.bounded_queue` — 需要"排队而不是拒绝"时，用有界队列实现整形，代价是延迟上升。

## 测试说明

- 配额测试：固定速率请求，断言放行数量符合配置
- 突发测试：桶空时突发请求，断言不超过容量
- 补充测试：断言随时间推移令牌按速率恢复
- 并发测试：多线程同时取令牌，断言总量不超发
- 拒绝测试：断言返回明确的限流错误（如 429）与可提示的重试时间

## 实现注意

- 令牌桶允许突发（容量即突发额度），漏桶不允许突发（输出平滑）
- 限流策略应可按环境配置；生产值不要硬编码
- 限流是"公平性"工具：多租户系统里要防止一个大租户吃满全局配额
- 限流器的判定逻辑要与业务重试策略配套，否则客户端会立刻重试把限流变成风暴
