# 事务发件箱（Transactional Outbox）

- 资产 ID：`pattern.integration.transactional_outbox`
- 类型：`pattern`（设计模式）
- 分类：`integration`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`TransactionalOutbox`、`事务发件箱`、`outbox pattern`、`发件箱模式`

## 一句话定位

用"同一事务里一起写库和写消息表"换掉"先写库再发消息"这一拍不一致，代价是至少一次投递。

订单提交成功后进程崩溃，消息没发出去，库存系统永远不知道；反过来先发消息再写库，消息对应的订单可能不存在。

## 典型源文件形状

```rust
// 同一个本地事务：写业务表 + 写 outbox 表
pub fn place_order(uow: &mut dyn UnitOfWork, order: &Order) -> Result<(), AppError> {
    uow.orders().save(order)?;
    uow.outbox().enqueue(&OutboxMessage {
        topic: "order.placed",
        key: order.id.to_string(),
        payload: serde_json::to_vec(order)?,
    })?;
    Box::new(uow).commit()
}

// 独立的投递器：轮询 outbox 表并转发到消息中间件
```

## 适用条件

- 需要把状态变更可靠地通知到其它系统
- 业务写入与消息发送必须保持原子性
- 能够接受"至少一次"投递并让消费者去重
- 没有可用的分布式事务
- 系统边界：只保证"消息与业务写入在同一事务落库"这一段；从发件箱到消息中间件的投递、以及中间件自身的可用性都不在边界内。

## 反例

- 不需要跨系统通知——发件箱是纯额外复杂度
- 接收方要求"恰好一次"——发件箱只能做到至少一次，需要接收端幂等
- 消息量极大且延迟敏感——发件箱的轮询与投递延迟可能不可接受
- 本地事务本身就不可回滚（比如已在外部系统产生副作用）——发件箱帮不上忙

## 并发风险

- 多个投递器实例同时轮询时，必须用"抢占 + 租约"避免同一消息被并发投递（至少一次的前提）
- 投递器崩溃后租约过期，消息会被重新投递——这正是期望行为，接收端必须能去重
- 发件箱表的清理要分批进行，长事务锁表会阻塞业务写入
- 同一聚合的多条消息应保持顺序：按聚合键分区或在同一分区内保序
- 投递器不要在持锁状态下发网络请求，否则会把慢 broker 的延迟传导成锁等待

## 替代方案

- `pattern.integration.publish_subscribe` — 发布订阅定义消息如何流转，发件箱定义消息如何被可靠地产生，两者常配合。
- `pattern.integration.idempotent_consumer` — 发件箱只能保证至少一次，幂等消费者是它的必要配套。

## 测试说明

- 原子性测试：故意让业务写入失败，断言 outbox 表里没有留下消息
- 投递测试：断言投递器会把待发消息转出，且成功后标记或删除
- 崩溃恢复测试：投递器在发送后、标记前崩溃，断言消息会被重投（至少一次）
- 并发投递测试：两个投递器同时工作，断言同一条消息不会被两个投递器同时处理（用租约验证）
- 顺序测试：同一聚合键的消息按序发出

## 实现注意

- 发件箱不是"消息队列的替代品"，它是"可靠产出消息"的一层，通常仍然需要 broker
- "至少一次 + 消费者幂等"是最常见的组合，不要试图在发件箱侧实现恰好一次
- 消息体要有稳定的事件 id 与聚合键，便于去重与保序
- 发件箱表要监控积压量，积压意味着投递器故障
