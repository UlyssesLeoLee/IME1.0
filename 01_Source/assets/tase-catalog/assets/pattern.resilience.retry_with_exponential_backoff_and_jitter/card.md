# 带指数退避与抖动的重试（Retry with Exponential Backoff and Jitter）

- 资产 ID：`pattern.resilience.retry_with_exponential_backoff_and_jitter`
- 类型：`pattern`（设计模式）
- 分类：`resilience`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`RetryWithBackoff`、`指数退避重试`、`exponential backoff jitter`、`重试退避`

## 一句话定位

失败后不是立刻再试，而是按指数增长的间隔等待并加入随机抖动，把重试压力摊开。

下游短暂抖动时立刻重试会形成"惊群"：所有客户端在同一毫秒再次冲击刚恢复的服务，把它再次打垮。

## 典型源文件形状

```rust
pub fn backoff_delays(base: Duration, cap: Duration, attempt: u32) -> Duration {
    let exp = base.saturating_mul(2u32.saturating_pow(attempt));
    let exp = exp.min(cap);
    // full jitter：在 [0, exp] 之间随机取等待时长
    let jitter = rand::random::<u64>() % (exp.as_millis() as u64 + 1);
    Duration::from_millis(jitter)
}
```

## 适用条件

- 失败是瞬时的（网络抖动、限流、临时不可用）
- 操作是幂等的，或带幂等键
- 调用方能接受延迟换取成功率
- 错误类型可以区分"可重试"与"不可重试"
- 系统边界：只负责"失败后等多久再试"，不负责判断该不该重试（错误分类在调用方），也不负责限制重试带来的额外流量（需隔离舱或限流配合）。

## 反例

- 操作不幂等且无幂等键——重试可能造成重复扣款/重复发货
- 错误是确定性的（400、404、鉴权失败）——重试永远失败
- 调用在交互式路径上且用户等不起——重试会放大等待时间
- 下游已经熔断——重试会绕过断路器的保护意图

## 并发风险

- 重试必须限制并发总量：每个调用方各自重试会放大总流量，需配合信号量或隔离舱
- 重试要放在"单一责任层"（客户端内），不要让上层调用栈层层重试，否则尝试次数是乘法关系
- 重试与超时必须同时设上限，保证总时长可预期（总超时 = 单次超时 × 次数 + 退避）
- 抖动是必需的：没有抖动，所有客户端会在同一时刻重试，形成周期性尖峰
- 重试上下文要能被取消：调用方取消或超时时，正在等待的退避应立即结束

## 替代方案

- `pattern.resilience.circuit_breaker` — 重试处理短暂故障，断路器处理持续故障；两者配合使用效果最好。
- `pattern.resilience.bulkhead` — 隔离舱限制重试放大后的并发总量，避免重试把资源耗尽。

## 测试说明

- 用假依赖注入可重试与不可重试错误，断言只在可重试时重试
- 断言重试次数不超过上限，且总耗时不超过总超时
- 断言退避间隔单调增长且不超过上限（用注入的时钟/随机源做确定性测试）
- 断言抖动存在：多次采样的等待时长不全相同（统计意义上）
- 断言取消后不再继续重试

## 实现注意

- 退避基数与上限要根据下游的恢复时间设定，30 秒以上的重试对交互式请求通常无意义
- "全抖动"（在 [0, 指数退避] 间随机）比"等抖动"更能削峰
- 重试次数要按幂等性确定：读操作可以多试，写操作要配合幂等键
- 不要把重试当成可靠性方案的核心；可靠性应来自架构（发件箱、幂等消费）
