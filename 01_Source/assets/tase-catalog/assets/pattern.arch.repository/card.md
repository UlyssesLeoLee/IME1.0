# 仓储（Repository）

- 资产 ID：`pattern.arch.repository`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Repository`、`仓储模式`、`repository pattern`

## 一句话定位

给聚合根一个"像集合一样"的存取入口，把表结构、SQL、ORM 与连接管理挡在仓储实现内部。

领域对象里出现裸 SQL 与表名，换存储引擎要改几十个业务文件；仓储把"怎么存"与"是什么"分开。

## 典型源文件形状

```rust
pub trait OrderRepository: Send + Sync {
    fn save(&self, order: &Order) -> Result<(), RepoError>;
    fn by_id(&self, id: OrderId) -> Result<Option<Order>, RepoError>;
}

pub struct SqlOrderRepository { pool: sqlx::Pool<Postgres> }
```

## 适用条件

- 领域模型需要与存储技术解耦
- 聚合有清晰边界，存取以聚合为单位
- 需要用内存实现替换存储做单元测试
- 存储访问需要统一的错误语义、事务参与与审计
- 系统边界：只负责单个聚合的存取，不负责事务边界（由工作单元负责）、不负责查询建模（由 CQRS 读侧负责），也不缓存聚合状态。

## 反例

- 只是简单的 CRUD 后台——仓储会徒增一层，直接用数据访问层
- 查询需求复杂且报表多——通用仓储会变成"另一个 SQL 包装器"，不如直白地写查询
- 一个仓储承载多个聚合——边界不清会导致加载出巨大的对象图
- 为了"领域 purity"把简单的读取也藏起来——收益不足时不如直白

## 并发风险

- 仓储通常被多线程共享，其实现必须 `Send + Sync`；数据库连接池本身线程安全
- 读写分离时读副本有复制延迟，"写后立即读"可能读到旧值——需要在接口层说明一致性语义
- 仓储若在实现里隐式开启事务，会破坏 Unit of Work 的事务边界，应由工作单元控制
- 共享可变缓存（如仓储内部的查询缓存）必须同步，否则会出现脏读
- 长事务会占住连接池槽位：仓储方法应保持短事务，跨多仓储的写操作交给 Unit of Work

## 替代方案

- `pattern.arch.unit_of_work` — 仓储负责"存取单个聚合"，工作单元负责"一次事务里的多个仓储"；两者配套使用。
- `pattern.arch.cqrs` — 读写分离且查询模型独立时，用 CQRS 的读侧替代通用仓储。

## 测试说明

- 用内存实现写领域层单元测试：断言保存后能按 id 读回，字段完整
- 对 SQL 实现写集成测试：真实数据库上跑同一套契约
- 测试错误路径：连接失败、唯一键冲突、找不到记录时的错误类型
- 测试仓储不会泄漏底层异常（断言错误被映射成仓储自己的错误枚举）
- 断言一次聚合保存是一次原子写入（不会出现部分字段被更新的中间态）

## 实现注意

- 仓储是"聚合的持久化"，不是"表的映射"；一个表可能有多个仓储，一个仓储也可能跨表
- 不要在仓储里放业务规则；规则属于领域对象或应用服务
- 返回 DTO 而非 ORM 实体，可避免持久化模型污染领域模型（另见读副本更新）
- 仓储抽象的价值随领域复杂度上升；不要给每个简单查询都建仓储方法
