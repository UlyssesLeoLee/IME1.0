# 计数排序（Counting Sort）

- 资产 ID：`algorithm.sorting.counting_sort`
- 类型：`algorithm`（算法）
- 分类：`sorting`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`counting_sort`、`计数排序`、`计数`

## 一句话定位

不比较键值，而是数一遍每个键有多少个，再按顺序把元素摆回去。

处理几百万条固定长度（0~255）的记录时，比较排序做了几千万次比较，而键的范围其实很小。

## 典型源文件形状

```text
counting_sort(a, k):                // 键在 [0, k)
    count = array of k zeros
    for x in a: count[key(x)] += 1
    for i = 1..k: count[i] += count[i-1]   // 前缀和
    out = array of len(a)
    for x in reversed(a):                 // 倒序回填以保持稳定
        count[key(x)] -= 1
        out[count[key(x)]] = x
    return out
```

## 适用条件

- 键是范围很小的整数（字节、字符、0~255 的枚举）
- 数据量大且键分布密集
- 需要线性时间（比较排序做不到）
- 数据可以被整体载入内存

## 反例

- 键值范围大——O(k) 的计数数组会超出内存
- 键是浮点数或自定义对象——必须先映射到整数索引
- 数据量很小——比较排序的常数更小
- 键分布稀疏（如 0 和 10^9 混杂）——不如先离散化或改用基数排序

## 并发风险

- 计数排序需要一块连续的计数数组，多线程共享写入同一数组需要按分片 + 归并
- 标准做法是并行分块统计后合并前缀和，但实现复杂度高
- 原地回填阶段无法并行（写位置依赖全局前缀和）
- 实践中并行收益有限，单线程计数排序已接近内存带宽上限

## 替代方案

- `algorithm.sorting.radix_sort` — 键范围较大时，基数排序按位拆分，可避免 O(k) 的大数组。
- `algorithm.sorting.merge_sort` — 键不可映射到小整数域时，用通用的比较排序。

## 测试说明

- 与标准库排序交叉比较，断言结果一致
- 键全相同、键覆盖 0 与 k-1 两端
- 空数组、单元素
- 稳定性测试：用 (key, index) 排序并断言相等键的顺序保持
- 断言计数数组大小与键范围匹配，越界键会被检测到

## 实现注意

- 优先标准库/成熟库：Rust 标准库没有计数排序，排序用 `sort_unstable_by_key`；需要线性排序时可用 `bucket` 生态的成熟 crate，注意许可
- 复杂度：时间 O(n + k)，额外空间 O(k)；非比较排序
- 稳定性：稳定（前提是从后往前回填）
- 内存：计数数组是 O(k)，键范围是主要约束
- 溢出：计数与前缀和要用能容纳 n 的类型（`usize`），n 很大时前缀和不会溢出但计数数组下标需检查
- 极端输入：键集中在一个值上时仍需 O(k) 时间与空间初始化
- 并发安全：原地回填阶段不可并行；共享计数数组需同步
- 限制：仅适用于小整数域；不适用于比较对象
