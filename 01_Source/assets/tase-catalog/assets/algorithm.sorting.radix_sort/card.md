# 基数排序（Radix Sort）

- 资产 ID：`algorithm.sorting.radix_sort`
- 类型：`algorithm`（算法）
- 分类：`sorting`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`radix_sort`、`基数排序`、`LSD`、`MSD`

## 一句话定位

把整数键拆成若干位，逐位做稳定的计数排序，用"多趟稳定排序"代替"一次比较排序"。

排序几百万条固定宽度记录时，比较排序的 O(n log n) 比较次数成为瓶颈，而键其实是定长整数。

## 典型源文件形状

```text
radix_sort_lsd(a, b):                // b = 基数（常用 256）
    max_digit = digit_count(max(a))
    for d = 0..max_digit:
        a = counting_sort_by_digit(a, d, b)   // 稳定
    return a

counting_sort_by_digit(a, d, b):
    count = array of b zeros
    for x in a: count[(x / b^d) mod b] += 1
    for i = 1..b: count[i] += count[i-1]
    out = new array of len(a)
    for x in reversed(a):
        k = (x / b^d) mod b
        count[k] -= 1
        out[count[k]] = x
    return out
```

## 适用条件

- 键是定长整数或可无损转换为定长整数的字节串
- 数据量大、比较成本高，希望线性时间
- 需要稳定排序（多趟排序依赖稳定性）
- 数据能整体放入内存

## 反例

- 键是变长字符串——MSD 基数排序可以处理，但实现复杂、常数不一定优于比较排序
- 键是浮点数——需要 IEEE754 位模式的特殊处理，否则负数与 NaN 会出错
- 数据量小——比较排序的常数更小
- 键分布使有效位宽很大（如 64 位稀疏值）——趟数增加，优势消失

## 并发风险

- 每一趟内部（计数 + 回填）基本是串行的，趟与趟之间有数据依赖，无法简单并行
- MSD 版本可以从最高位开始按桶并行处理同层的子数组，理论并行度更高
- 多线程共享输出数组的同一趟回填需要分桶 + 合并，实现复杂度高
- 实践上并行基数排序的收益通常不如并行归并

## 替代方案

- `algorithm.sorting.counting_sort` — 基数排序的每一趟本质上就是一次计数排序，单趟基数排序即计数排序。
- `algorithm.sorting.merge_sort` — 键不是整数或需要稳定性外的其它性质时，用归并排序更通用。

## 测试说明

- 与标准库排序交叉比较，断言结果一致
- 含 0、负数（需偏移处理）、最大值边界
- 空数组、单元素、全相同
- 不同位宽的键（8 位、16 位、32 位）
- 断言多趟排序的稳定性：每一趟都必须稳定

## 实现注意

- 优先标准库/成熟库：Rust 无内置基数排序，成熟 crate 如 `radix_sort` 可用，需核查其许可与维护状况
- 复杂度：O(d(n + b))，d 为位数、b 为基数；最坏 O(d n)
- 稳定性：稳定（前提是每一趟稳定）
- 内存：O(n + b) 辅助空间
- 溢出：位提取 `(x / b^d) mod b` 要用无符号运算避免负数与溢出；大位宽用 `u128` 中转
- 极端输入：全相同值需要完整 d 趟；稀疏高位会浪费趟数
- 并发安全：单趟内共享数组不可并发写；并行化需按桶切分
- 限制：仅适用于定宽整数键；字符串需 MSD 变体；浮点需特殊处理
