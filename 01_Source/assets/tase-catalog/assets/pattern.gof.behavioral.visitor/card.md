# 访问者（Visitor）

- 资产 ID：`pattern.gof.behavioral.visitor`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Visitor`、`访问者模式`、`visitor pattern`

## 一句话定位

把"对不同类型元素的多种操作"集中到访问者里，使元素类保持稳定、操作可以不断增加。

AST 里要支持"求值""类型检查""代码生成""格式化"四种操作，若都写在节点类里，节点类会被撑爆且每加一种操作就改所有节点。

## 典型源文件形状

```rust
pub enum Node {
    Num(f64),
    Add(Box<Node>, Box<Node>),
}

pub trait Visitor {
    fn visit_num(&mut self, n: f64);
    fn visit_add(&mut self, l: &Node, r: &Node);
}

impl Node {
    pub fn accept(&self, v: &mut dyn Visitor) {
        match self {
            Node::Num(n) => v.visit_num(*n),
            Node::Add(l, r) => v.visit_add(l, r),
        }
    }
}
```

## 适用条件

- 元素类型集合稳定且数量不多
- 操作种类多且会持续增加
- 无法或不应修改元素类（例如它们来自第三方库或被大量代码依赖）
- 需要在同一棵结构上执行多种不同遍历

## 反例

- 元素类型经常增加——每加一种元素要改所有访问者，成本高于收益
- 只有一个元素类型——直接写方法
- 只有一个操作——不需要访问者
- 操作与元素类型的组合是稀疏的——大部分访问者方法会空实现，说明抽象不划算

## 并发风险

- 访问者通常在遍历期间被 `&mut` 持有，因此同一棵树不能被两个访问者同时遍历（除非克隆或用内部可变性）
- 访问者若积累状态（计数器、输出缓冲），该状态是访问者实例自己的，不应放到共享全局
- 若在多线程上并行遍历同一棵树，需要每线程一份访问者与只读树
- 访问者回调若触发对树的结构修改，会破坏遍历；应禁止或使用 copy-on-write

## 替代方案

- `pattern.gof.behavioral.strategy` — 策略是"对一个对象换算法"，访问者是"按元素类型分派多种操作"；分派维度不同。
- `pattern.gof.behavioral.iterator` — 若需求只是顺序遍历而不需要按类型分派，迭代器更简单。

## 测试说明

- 对每种元素类型断言访问者被正确分派（用假访问者记录调用）
- 断言遍历顺序符合结构定义
- 对空结构、单节点、混合结构写用例
- 断言访问者不需要修改元素类（可用编译期或代码审查保证）

## 实现注意

- 设计书明确要求：本卡必须写清"扩展维度的权衡"——加操作很便宜，加元素类型很贵
- Rust 中枚举 + `match` 往往能同时表达"多操作 + 多类型"，且有穷尽性检查；访问者的优势主要在"无法修改元素类"时
- 访问者把"类型分派"从元素类搬到访问者，代价是新增元素类型要改所有访问者
- 双分派在 Rust 里通过 `match` + 回调实现，不要指望有动态重载
