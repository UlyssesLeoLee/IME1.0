# 读副本更新（Read-Copy-Update）

- 资产 ID：`pattern.integration.read_copy_update`
- 类型：`pattern`（设计模式）
- 分类：`integration`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`ReadCopyUpdate`、`读副本更新`、`read copy update`、`RCU`

## 一句话定位

让读者永远不被写者阻塞：写者复制一份再改，然后原子地把指针换过去。

配置或路由表在高频读取的同时偶尔被改，用互斥锁保护会让所有读请求排队。

## 典型源文件形状

```rust
use std::sync::atomic::{AtomicPtr, Ordering};
use std::sync::Arc;

pub struct RouteTable {
    head: AtomicPtr<Arc<RouteSet>>,
}

impl RouteTable {
    pub fn read(&self) -> Arc<RouteSet> {
        // 读侧只做原子取指针，再克隆引用计数
        let p = self.head.load(Ordering::Acquire);
        unsafe { (*p).clone() }
    }
}
```

## 适用条件

- 读远多于写，且读延迟敏感
- 状态对象较大但更新频率低（路由表、配置快照、特征集）
- 需要读侧完全无锁、无阻塞
- 可以接受写侧的复制成本与额外内存
- 系统边界：只保证读者看到的是一个完整一致的快照，不保证"读-改-写"这一复合操作的原子性，也不负责写者之间的冲突仲裁。

## 反例

- 状态很小且更新很频繁——每次更新都复制不划算
- 内存紧张——多版本共存会放大占用
- 需要"读取后再决定写什么"的复合原子操作——RCU 不提供，需要额外加锁或用事务
- 对象内部含不可克隆资源（句柄、连接）——复制语义不成立

## 并发风险

- 核心不变式：读者看到的一定是某个完整版本，不会看到撕裂的中间状态
- 内存序必须正确：发布用 `Release`、读取用 `Acquire`，否则可能读到未完全初始化的数据
- 旧版本不能立即释放——必须等所有读者离开；用引用计数、epoch/RCU 机制或 hazard pointer
- 写者之间要互斥，否则两个写者会互相覆盖（丢失更新）
- 读者拿到快照后应按不可变使用；不要在读取后原地修改共享状态
- 销毁旧版本时不能有读者仍在使用，否则是 use-after-free

## 替代方案

- `pattern.integration.cache_aside` — 旁路缓存是"缓存外部数据"，读副本更新是"用不可变快照替换共享状态"，问题域不同。
- `pattern.gof.structural.flyweight` — 享元共享不可变数据以省内存；RCU 用不可变版本 + 原子替换来免锁，二者常配合。

## 测试说明

- 一致性测试：并发读写下，读者每次读到的快照都必须是某个完整合法版本
- 版本单调性测试：断言读到的版本号不倒退
- 压力测试：多读者 + 多写者长时间运行，TSAN 下无告警
- 内存测试：断言旧版本在读者退出后被释放（用弱引用或内存统计观察）
- 断言写者互斥：并发写不会丢失更新

## 实现注意

- RCU 在内核与数据库里有成熟实现，应用层手写要非常小心内存序与生命周期
- Rust 里 `Arc` + `RwLock` 常常已足够，不必手写原子指针
- 不可变快照是前提：快照内部若含可变共享状态，RCU 的保证就不成立
- RCU 解决的是"读不阻塞"，不解决"复合操作原子性"，后者仍需锁或事务
