# 外观（Facade）

- 资产 ID：`pattern.gof.structural.facade`
- 类型：`pattern`（设计模式）
- 分类：`structural`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Facade`、`外观模式`、`facade pattern`

## 一句话定位

在子系统前放一个"总台"，把多次、跨组件的调用编排成一次业务意图明确的调用。

用户要完成"注册账号"这件事，需要依次调用用户服务、权限服务、审计服务、通知服务，调用方被迫知道内部流程与顺序。

## 典型源文件形状

```rust
pub struct AccountService {
    users: UsersRepo,
    perms: PermsRepo,
    audit: AuditLog,
}

impl AccountService {
    pub fn register(&self, name: &str) -> Result<UserId, RegisterError> {
        let id = self.users.insert(name)?;
        self.perms.grant(id, "account:read")?;
        self.audit.record(id, "register")?;
        Ok(id)
    }
}
```

## 适用条件

- 一个业务动作需要跨多个子系统协作，调用顺序有讲究
- 调用方（尤其是上层 UI 或 Agent 工具层）不该了解子系统内部结构
- 希望降低系统对外暴露的接口面积与耦合面
- 需要为子系统提供更易用、更贴合业务语言的入口

## 反例

- 子系统只有一个——直接调用即可
- 外观变成了"第二个业务层"，与原有 service 层职责重叠——应合并而不是叠加
- 调用方确实需要绕过外观做精细控制——外观应保留对底层的显式访问或另设底层接口
- 为了"看起来整洁"把不相关的功能都塞进外观——外观会退化成上帝对象

## 并发风险

- 外观本身通常无状态，可共享；若外观缓存了子系统句柄，注意句柄的 `Send`/`Sync`
- 编排顺序里的失败处理要明确：若中途失败，已完成的前置步骤是否回滚？外观不应假装有事务
- 外观方法持有多个子系统锁时要固定加锁顺序，避免与子系统内部的锁形成环路
- 外观内的并行调用（如同时请求两个服务）要各自超时，单个慢依赖不能拖垮整体

## 替代方案

- `pattern.gof.structural.adapter` — 适配器解决"接口不兼容"，外观解决"接口太多太细"，二者常同时出现在防腐层里。
- `pattern.gof.structural.proxy` — 代理改变的是"访问方式"（远程/惰性/权限），外观改变的是"调用粒度"。

## 测试说明

- 对每个外观方法测试正常路径：断言各子系统的调用次数、顺序与参数
- 测试每个子系统失败的路径：断言错误被正确传播，且后续步骤没有被错误执行
- 断言外观没有把子系统细节泄漏到返回类型里（返回类型应是业务概念）
- 不要在外观测试里 mock 掉被编排的全部子系统，只保留真正需要验证的交互

## 实现注意

- 外观不是"必须的层"：如果调用方本来就知道流程，外观只是多一跳
- Rust 中外观通常是一个持有若干具体类型的结构体；泛型参数版本保留静态派发，动态版本更易组装
- 外观与事务边界要分清：跨多个数据源的写入应由 Unit of Work 负责，而不是外观
- 外观内部不要写业务分支判断，那属于领域层；外观只做编排
