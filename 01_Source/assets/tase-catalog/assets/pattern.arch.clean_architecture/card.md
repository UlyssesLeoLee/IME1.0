# 整洁架构（Clean Architecture）

- 资产 ID：`pattern.arch.clean_architecture`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`CleanArchitecture`、`整洁架构`、`clean architecture`

## 一句话定位

用"依赖只能朝内"的规则把业务核心圈起来，外层技术细节围绕它组织，核心可以被替换与独立测试。

业务规则里混进了 ORM 注解、HTTP 处理与配置读取，换数据库或换框架就牵动全部业务代码。

## 典型源文件形状

```rust
// 内层：实体与用例，只依赖标准库与本层
pub struct Checkout { pub total: f64 }

pub struct PlaceOrderUseCase {
    price_sheet: Box<dyn PriceSheet>,   // 端口（外层实现）
}

impl PlaceOrderUseCase {
    pub fn execute(&self, cart: &Cart) -> Result<Checkout, CheckoutError> {
        let total = self.price_sheet.total(cart)?;
        Ok(Checkout { total })
    }
}
```

## 适用条件

- 业务规则复杂且必须长期稳定，基础设施会频繁替换
- 需要同一业务逻辑服务于多个终端（CLI、GUI、Web、Agent 工具）
- 团队规模较大，需要清晰的职责边界
- 测试要求核心逻辑能脱离 IO 快速运行
- 系统边界：规定的是源码的依赖方向，不规定部署形态、进程边界、通信协议与技术选型；哪一层可以直接依赖外部库，需要团队另立规矩并用检查工具守住。

## 反例

- 项目规模小、生命周期短——层级成本大于收益
- 领域模型没有真正独立的规则（只是数据搬运）——此时"内层"是空的
- 强行分层导致每层都要写一次同样的 DTO——应减少重复建模，而不是加更多层
- 边界靠口号维持、无人评审——依赖规则必须能被工具或评审检查

## 并发风险

- 内核层应尽量保持无状态与线程安全：共享状态放外层适配器
- 端口（trait）若返回内部可变的共享对象，会把并发问题泄漏进内核；返回不可变快照更安全
- 用例对象若被多线程共享，其依赖必须 `Send + Sync`；用 `&self` 而非 `&mut self` 的用例更易并行
- 跨层调用方向必须严格朝内：内核回调外层（例如通过 trait 端口）要小心避免形成环

## 替代方案

- `pattern.arch.hexagonal_architecture` — 六边形架构是整洁架构的"端口与适配器"变体，边界画法不同，理念接近。
- `pattern.arch.dependency_injection` — 依赖注入是实现依赖规则的手段；整洁架构是依赖规则的架构风格。

## 测试说明

- 核心层单元测试：不启动数据库、不发网络请求，断言纯业务规则
- 外层集成测试：每个适配器单独测自己的契约（仓储、HTTP 客户端）
- 端到端测试：验证组装后的应用按场景工作
- 用架构测试（依赖方向检查）防止内核反向依赖外层

## 实现注意

- 设计书明确：整洁架构属于现代工程模式，不在 GoF 23 之列
- 整洁架构的四条规则：依赖只朝内、只用高层定义低层、策略不依赖细节、细节依赖策略
- "依赖倒置"不是"每个东西都有接口"；只在确有替换需求处定义端口
- 不要为了分层把简单逻辑拆散到 6 个 crate，编译时间与认知负担都会上升
