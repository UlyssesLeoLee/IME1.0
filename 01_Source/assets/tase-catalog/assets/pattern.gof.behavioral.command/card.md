# 命令（Command）

- 资产 ID：`pattern.gof.behavioral.command`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Command`、`命令模式`、`command pattern`

## 一句话定位

把"要做什么"变成一个可传递、可存储、可回放的值，从而支持撤销、排队、审计与重试。

UI 的撤销栈、任务队列、审计日志都要求"刚才那个操作"能被保存下来并在稍后原样执行——直接调用函数做不到。

## 典型源文件形状

```rust
pub trait Command {
    fn execute(&mut self);
    fn undo(&mut self) { }
}

pub struct SetZoom {
    pub doc: Rc<RefCell<Doc>>,
    pub old: f64,
    pub new: f64,
}

impl Command for SetZoom {
    fn execute(&mut self) { self.doc.borrow_mut().zoom = self.new; }
    fn undo(&mut self) { self.doc.borrow_mut().zoom = self.old; }
}
```

## 适用条件

- 操作需要被排队、延迟执行或跨进程传递
- 需要撤销/重做（命令必须记录足够的状态以逆转）
- 需要操作审计日志，且日志里要能重放
- 同一个操作要绑定不同参数副本（例如定时任务）

## 反例

- 只是一次性的同步调用——用闭包或普通函数，避免对象化开销
- 操作不可逆且不需要撤销——命令对象只会徒增样板代码
- 命令需要携带大量可变上下文时——命令会变成"用对象写的函数"，应改用专门的用例/作业模型
- 为了用命令而把所有方法调用都包一层——收益远低于噪音

## 并发风险

- 命令对象是"待执行的值"，本身应尽量不可变或独占；不要把同一个命令实例交给多个执行者
- 若命令持有 `Rc<RefCell<..>>`，跨线程会直接不安全；需要跨线程时应改用 `Arc<Mutex<..>>` 或把状态快照放进命令
- 撤销栈本身是共享可变状态，多线程下需要 `Mutex` 保护；且撤销顺序必须严格逆序
- 命令的 `execute` 应尽量幂等或明确"重试安全"，否则队列重投会重复产生副作用

## 替代方案

- `pattern.gof.behavioral.strategy` — 策略替换的是"怎么做"，命令封装的是"做什么"；命令需要参数化、排队、撤销时选命令。
- `pattern.arch.unit_of_work` — 需要"一批命令作为事务单元提交/回滚"时，用 Unit of Work 承载命令列表。

## 测试说明

- 对每个命令测 `execute` 改变的状态与 `undo` 恢复的状态（成对断言）
- 断言撤销栈按逆序撤销，且连续撤销后状态回到初始
- 测试命令的序列化/重放（若支持持久化），断言重放结果与原执行一致
- 测试重复执行的语义：明确是幂等还是禁止

## 实现注意

- 撤销不是"反向调用"：命令必须自己保存逆操作所需的旧值
- 命令的 `undo` 失败要有定义（部分撤销、拒绝撤销）
- 不要在命令里直接做 IO；命令应只描述意图，执行由执行器负责
- Rust 中命令通常是拥有数据的结构体，便于克隆与持久化
