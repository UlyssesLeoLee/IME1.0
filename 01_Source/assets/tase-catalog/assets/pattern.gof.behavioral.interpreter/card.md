# 解释器（Interpreter）

- 资产 ID：`pattern.gof.behavioral.interpreter`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Interpreter`、`解释器模式`、`interpreter pattern`

## 一句话定位

给一小块自定义语言定义"词法-语法-求值"三件套，让配置、规则或脚本可以被解析并安全地执行。

把过滤条件、告警规则、权限表达式硬编码在代码里，用户无法自助调整；写一个受限的小语言就能让规则变成数据。

## 典型源文件形状

```rust
pub enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}

impl Expr {
    pub fn eval(&self) -> f64 {
        match self {
            Expr::Num(n) => *n,
            Expr::Add(a, b) => a.eval() + b.eval(),
            Expr::Mul(a, b) => a.eval() * b.eval(),
        }
    }
}
```

## 适用条件

- 存在一门小型、稳定、领域专用的语言（过滤表达式、规则、模板）
- 语言的用户需要动态组合规则而不改代码
- 文法足够小，可以清楚地定义并测试
- 求值过程需要可解释（能报出是哪一条规则出错）

## 反例

- 只是配置几个参数——用结构化配置（JSON/TOML）加校验更简单
- 用户输入不可信——不要让用户写表达式在进程里求值，改用受限的查询语言或参数化 API
- 语言特性需要不断扩展——写解释器的成本会超过收益
- 已有成熟表达式库（如 CEL、jq）——优先复用成熟库而不是自写

## 并发风险

- 解释器本身通常无状态，可在多线程中并行求值；但若文法或符号表是全局可变的，就有竞争风险
- 解释执行的 AST 若包含共享的可变节点（如 `RefCell`），并发求值同一棵树不安全
- 递归求值深度受输入控制：不可信输入必须限制深度与节点数，否则可能栈溢出或造成 DoS
- 符号表/作用域若用全局哈希表，需要同步或每线程一份

## 替代方案

- `pattern.gof.behavioral.chain_of_responsibility` — 当"规则"不需要复杂表达式、只要顺序匹配时，责任链更简单。
- `pattern.arch.dependency_injection` — 若需求只是"让外部配置生效"，注入配置对象通常比自写解释器更稳。

## 测试说明

- 为文法写覆盖测试：每个产生式至少一条正例，多条负例
- 测试求值结果与预期值（覆盖各种运算组合）
- 测试错误处理：语法错误、未知符号、类型不匹配都要有明确报错
- 做健壮性测试：深层嵌套、极端数值、超长输入不 panic、不栈溢出
- 若接受不可信输入，做 fuzz 测试（随机字节不应导致 panic 或挂死）

## 实现注意

- 自写解释器前先找成熟库：CEL、JSONPath、jq 风格库能省掉大量安全与维护成本
- 解释器模式常与访问者组合：AST 节点负责数据，访问者负责求值动作
- 递归下降解析器实现简单，但要注意深度限制与错误信息位置
- 不要在解释器里求值任意代码；这属于自造的安全漏洞
