# 事件溯源（Event Sourcing）

- 资产 ID：`pattern.arch.event_sourcing`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`EventSourcing`、`事件溯源`、`event sourcing`

## 一句话定位

不存"当前值"，只存"发生过什么"，状态是事件流的投影。

审计要求"任何时刻的状态都能被解释"，审计要求"任何变更都留痕"，传统做法是额外写日志表，两者可能对不上。

## 典型源文件形状

```rust
pub enum OrderEvent {
    Placed { order_id: OrderId, items: Vec<Item> },
    Paid { order_id: OrderId, amount: f64 },
    Shipped { order_id: OrderId },
}

pub fn reduce(events: &[OrderEvent]) -> Order {
    events.iter().fold(Order::default(), |mut o, e| {
        match e {
            OrderEvent::Placed { order_id, items } => o.place(*order_id, items.clone()),
            OrderEvent::Paid { .. } => o.mark_paid(),
            OrderEvent::Shipped { .. } => o.mark_shipped(),
        }
        o
    })
}
```

## 适用条件

- 必须保留完整历史（审计、合规、财务）
- 需要"时间旅行"查看或重建任意时刻的状态
- 状态变化本身包含丰富信息，不能压缩成一个当前值
- 领域事件粒度稳定，事件模式演进有规划
- 系统边界：以事件流为真相来源，不负责事件的分发（由发布订阅负责）、不负责跨聚合的原子性（由 Saga 负责），读模型的查询能力也在边界之外。

## 反例

- 只需要当前状态——事件溯源会带来回放成本与运维复杂度
- 事件需要被修正或删除（如用户要求删个人数据）——需要额外的补偿/墓碑机制
- 读多写少且查询复杂——事件溯源的查询层建设成本很高
- 领域模型还在频繁变化——事件模式一旦被外部消费就难以更改

## 并发风险

- 同一聚合的事件追加必须串行化：典型做法是"聚合版本号 + 乐观并发控制"，冲突时重放并重试
- 投影器（把事件变成读模型）必须幂等，且要能容忍乱序与重复投递
- 事件日志追加与投影更新不在同一事务里（跨存储），因此最终一致是常态，必须显式设计
- 快照（snapshot）只是加速回放的缓存，不是真相来源；快照与事件之间要有一致性校验
- 多线程回放同一事件流时，读模型写入要用 upsert 或按版本号做幂等判定

## 替代方案

- `pattern.arch.cqrs` — CQRS 分离读写，事件溯源提供写侧的真相来源；两者互补但可独立使用。
- `pattern.integration.publish_subscribe` — 发布订阅是事件分发机制；事件溯源要求事件持久且可回放，分发只是其中一步。

## 测试说明

- 回放测试：给定事件序列，断言 reduce 出的状态正确
- 不变量测试：对随机事件序列断言领域不变量始终成立（性质测试）
- 投影幂等测试：重复与乱序投递同一事件，断言读模型不变
- 演进测试：用旧版本事件样本验证新版本代码仍能正确回放
- 快照一致性测试：断言"有快照 + 后续事件"与"全量回放"结果相同

## 实现注意

- 事件溯源的"事件"是领域事实（已发生），不是命令或通知；命名要用过去式
- 事件模式演进要一开始就规划：只加字段、不改语义，必要时提供 upcaster
- 删除个人数据（GDPR 类要求）与不可变事件流冲突，必须提前设计抹除/加密方案
- 没有事件溯源也能满足审计：追加一张不可变变更表往往已够用
