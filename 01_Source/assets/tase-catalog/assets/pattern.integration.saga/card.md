#  Saga（长事务编排）（Saga）

- 资产 ID：`pattern.integration.saga`
- 类型：`pattern`（设计模式）
- 分类：`integration`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Saga`、`saga pattern`、`长事务`、`saga orchestration`

## 一句话定位

承认分布式环境没有全局事务，改用"逐步提交 + 失败补偿"把长流程拉直。

下单要扣库存、扣款、发货、通知；第三个服务挂了，前两个已经提交了，只能各自补偿而不是整体回滚。

## 典型源文件形状

```rust
pub enum SagaStep {
    ReserveStock { sku: String, qty: u32 },
    ChargeCard { amount: f64 },
    CreateShipment { order_id: OrderId },
}

pub struct OrderSaga { done: Vec<SagaStep>, log: Vec<String> }

impl OrderSaga {
    pub fn compensate(&self, services: &dyn SagaServices) -> Result<(), SagaError> {
        // 逆序执行已成功步骤的补偿动作
        for step in self.done.iter().rev() { services.compensate(step)?; }
        Ok(())
    }
}
```

## 适用条件

- 一个业务流程跨越多个各自独立提交的服务（服务、数据库）
- 无法使用单一分布式事务（两阶段提交代价过高或不被支持）
- 每一步都能定义一个有意义的补偿动作（退款、释放库存、撤销订单）
- 业务可以接受中间状态短暂可见（最终一致）
- 系统边界：编排与补偿逻辑在边界内；"中间状态对用户是否可见、业务上可否接受"属产品定义，在边界之外；单库内可原子完成的流程也不该套用 Saga。

## 反例

- 所有操作在同一个事务资源里——用本地事务，不要用 Saga
- 补偿动作不可逆或代价极高（已发货、已发钱）——应先做业务前置校验，而不是事后补偿
- 流程很短且失败率极低——补偿代码的复杂度可能超过收益
- 需要严格隔离（中间状态绝不能被外部看到）——Saga 不提供隔离性

## 并发风险

- 编排式 Saga 需要一个协调者，其状态（已完成步骤、当前阶段）必须持久化，进程崩溃后要能恢复
- 补偿动作必须幂等：协调者重试时可能重复执行补偿
- 并发执行的多个 Saga 实例之间可能争抢同一资源（库存），补偿不能假设资源状态未变
- 协调者与各服务的通信要处理"请求已发出但响应丢失"的歧义，通常靠幂等键 + 查询确认
- 补偿失败时的处理策略（重试、告警、人工介入）必须显式设计，不能吞掉错误

## 替代方案

- `pattern.integration.transactional_outbox` — 事务发件箱解决"本地提交与消息发布"的原子性，通常与 Saga 配合使用（发件箱负责可靠投递步骤）。
- `pattern.arch.unit_of_work` — 工作单元保证单一资源内的原子性；Saga 覆盖跨资源的最终一致，二者不可互换。

## 测试说明

- 每个步骤的失败注入测试：断言已完成步骤被逆序补偿，且补偿失败会被上报
- 断言补偿是幂等的：重复执行补偿不产生额外副作用
- 协调者崩溃恢复测试：持久化状态足以从中断点继续或整体补偿
- 断言补偿顺序正确（后一步先补偿）
- 并发测试：两个 Saga 争抢同一资源时，最终状态不得出现负库存等不变量破坏

## 实现注意

- 编排（orchestration）适合流程复杂、需要全局视图的场景；协同（choreography）适合步骤少、耦合低的场景
- Saga 不提供隔离性，脏读是可能的；设计时要把中间状态对用户的影响考虑清楚
- 补偿动作要写成幂等的、可重试的，不能假设一次成功
- 不要把 Saga 当成"分布式事务的廉价替代"，它的复杂度集中在失败路径上
