# 幂等消费者（Idempotent Consumer）

- 资产 ID：`pattern.integration.idempotent_consumer`
- 类型：`pattern`（设计模式）
- 分类：`integration`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`IdempotentConsumer`、`幂等消费者`、`idempotent consumer`、`幂等消费`

## 一句话定位

把"重复处理同一条消息"设计成无害的，让消息系统只承诺至少一次，业务侧自己保证效果唯一。

消费成功但确认消息时进程崩溃，broker 会重投；如果处理逻辑是"给账户加 100 元"，就会多加一次。

## 典型源文件形状

```rust
pub fn handle(uow: &mut dyn UnitOfWork, msg: &PaymentCaptured) -> Result<(), AppError> {
    let key = msg.transfer_id;   // 稳定的业务幂等键
    if uow.dedup().seen(key)? {
        return Ok(());   // 已经处理过，直接确认
    }
    uow.accounts().credit(msg.account_id, msg.amount)?;
    uow.dedup().record(key)?;   // 与业务写入同一事务
    Ok(())
}
```

## 适用条件

- 消费链路是至少一次投递（消息队列、事务发件箱、网络重试）
- 处理逻辑会产生可观测的副作用（写库、扣款、发消息）
- 能找到一个稳定的业务幂等键（业务 id、请求 id）
- 幂等记录与业务写入能放在同一事务里
- 系统边界：只覆盖消费端"重复执行无害"，不保证消息不丢（那是生产端与 broker 的责任），也不替业务判断"这次重复是否真的无害"。

## 反例

- 投递恰好一次且链路可信——不需要幂等层
- 处理是纯计算、无副作用——重复执行天然无害
- 副作用发生在外部系统且无法查询确认——幂等无法保证，应改为让外部系统提供幂等键
- 用"内存里的 set 记录处理过的 id"——进程重启即失效，等于没有幂等

## 并发风险

- 幂等键必须在并发消费下可靠：两个消费者同时处理同一条消息时，"检查去重 + 写入副作用"要在同一事务或靠唯一约束
- 数据库唯一约束（对幂等键建唯一索引）是最后一道防线，比先查后写更可靠
- 内存去重表（`HashSet`/`Mutex<HashSet>`）只在单进程内有效，重启或扩容即失效，只能当缓存
- 幂等键要有过期策略，否则去重表无限增长；但过期时间必须大于消息可能的最长重投间隔
- 并发消费乱序时，去重表不能阻止"旧消息覆盖新状态"，需要版本号或时间戳校验

## 替代方案

- `pattern.integration.transactional_outbox` — 事务发件箱保证消息被可靠产出（至少一次），幂等消费者保证重复消费无害，两者配套。
- `pattern.integration.publish_subscribe` — 发布订阅定义消息流转方式，幂等消费者是消费侧的契约要求。

## 测试说明

- 重复投递测试：同一条消息处理两次，断言业务状态只变化一次
- 并发重复测试：两个线程同时处理同一消息（同一幂等键），断言只产生一次副作用
- 崩溃恢复测试：写入副作用后、记录去重前崩溃，重投后断言没有重复副作用
- 去重过期测试：断言过期后消息可被重新处理（且符合预期）
- 断言幂等键的生成规则是稳定的（同一业务事件重投时键不变）

## 实现注意

- 幂等不是"忽略重复"，而是"重复执行后结果相同"；两者语义不同
- 优先用业务自然键（转账 id、订单 id）而不是消息 id，除非消息 id 本身稳定
- 幂等键的存储要与副作用同事务，否则中间崩溃仍会重复
- 消费端幂等 + 生产端发件箱是达成"业务上恰好一次效果"的常见组合
