# 0-1 背包（0/1 Knapsack）

- 资产 ID：`algorithm.dp.knapsack_01`
- 类型：`algorithm`（算法）
- 分类：`dp`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`knapsack_01`、`0-1背包`、`背包问题`、`knapsack`

## 一句话定位

一维滚动数组 + 容量倒序遍历，逐件物品更新"容量不超过 j 时的最大价值"。

背包容量可能是几千、物品成百上千，直接按"第几件 × 容量"开二维数组会吃光内存。

## 典型源文件形状

```text
knapsack_01(values, weights, W):
    dp = array of size W+1 filled with 0
    for i in 0..n:
        for j in W down to weights[i]:     // 倒序：保证每件物品只用一次
            dp[j] = max(dp[j], dp[j - weights[i]] + values[i])
    return dp[W]
```

## 适用条件

- 物品不可分割且每件最多选一次
- 容量是整数且规模中等（几百到几万）
- 价值与重量都是整数
- 需要精确最优解（不是近似）

## 反例

- 容量非常大（如 10^9）——伪多项式算法不可行，需改用近似或按价值维度 DP
- 每件物品可重复选——改用完全背包（正序遍历）
- 只需要近似解——分数背包的贪心或启发式更省
- 物品很少但种类多且有其它约束——需要更复杂建模

## 并发风险

- DP 是纯计算，无共享状态，可安全并行（按物品分块需谨慎，容量维有依赖）
- 并行化常用技巧：先算"物品数的一半"的表，再用合并式 DP 合并两个半表
- 只读输入表在多线程下共享安全
- 容量维的依赖是"先物品后容量"，直接按容量分块并行会出错

## 替代方案

- `algorithm.dp.coin_change` — 完全背包（物品可重复）形态相同但遍历方向相反，也与找零问题同构。
- `algorithm.datastructure.binary_heap` — 若问题变为"取价值最高的 k 件且重量不限"，用堆更合适。

## 测试说明

- 与暴力枚举（小规模）交叉比较
- 容量为 0、物品为空、单件物品放不下
- 重量恰好等于容量、放得下但价值不优
- 重量为 0 的物品（价值为正时应被全部选中——注意倒序遍历下 j 不变，需确认实现）
- 随机大规模用例的性能回归（固定 n 与 W 的耗时上限）

## 实现注意

- 优先标准库/成熟库：背包没有标准库实现；成熟 crate 有 `knapsack`，引入前需核查许可
- 复杂度：时间 O(n·W)（伪多项式，取决于容量数值而非 log W），额外空间 O(W)
- 稳定性：不适用
- 内存：滚动数组 O(W)；W 很大时要评估（每项 8 字节，W=10^6 约 8 MB）
- 溢出：价值与 dp 值要用足够宽的类型（如 `i64`），价值累加可能溢出 `i32`
- 极端输入：W = 0、n = 0、重量为 0 的物品、价值为负（通常应过滤掉非正价值）
- 并发安全：纯计算；并行需用分治合并式 DP
- 限制：伪多项式复杂度；容量必须为整数
