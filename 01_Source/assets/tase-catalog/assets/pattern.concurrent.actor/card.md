# Actor（Actor）

- 资产 ID：`pattern.concurrent.actor`
- 类型：`pattern`（设计模式）
- 分类：`concurrent`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Actor`、`Actor模型`、`actor model`

## 一句话定位

每个 actor 独占自己的状态，外部只能发消息给它，于是"谁在改这份数据"永远只有一个答案。

多个线程共享一份状态并用锁保护，锁顺序、竞态与死锁的组合排查成本极高；actor 把并发问题换成消息设计问题。

## 典型源文件形状

```rust
pub struct Counter { count: u64 }

impl Counter {
    pub fn handle(&mut self, msg: Msg) -> Option<Reply> {
        match msg {
            Msg::Inc => { self.count += 1; None }
            Msg::Get => Some(Reply::Count(self.count)),
        }
    }
}

// 运行时负责把消息投递到 actor 的邮箱并串行处理
```

## 适用条件

- 状态需要被多方并发访问，且访问逻辑复杂
- 希望用"消息顺序"替代"锁顺序"来推理正确性
- 实体之间天然是事件驱动（订单、账户、会话、协作者）
- 需要把阻塞操作从共享状态中隔离出去
- 系统边界：actor 的边界内是"自己的状态 + 处理收到的消息"；跨 actor 的事务性一致、跨 actor 的查询与聚合都在边界之外，需要额外协议或读模型。

## 反例

- 状态只读或写者单一——普通结构体 + 锁或无锁结构更直接
- 需要高频、低延迟的共享访问——每次访问都变成消息往返
- 团队不熟悉消息驱动的心智模型——排查难度会高于收益
- 需要事务性跨实体原子操作——actor 之间没有共享事务，需要额外的协调协议

## 并发风险

- actor 内部状态只由自身线程修改，天然无数据竞争；不要把内部状态引用泄漏出去
- 单个 actor 串行处理消息，因此 actor 数量决定并行度：热点 actor 会成为瓶颈
- 消息处理里不要做阻塞 IO，否则该 actor 的所有后续消息都会积压
- actor 之间循环发消息会互相阻塞；死锁表现为所有相关 actor 都停止处理
- 邮箱（mailbox）通常有界：满时发送方要等待或丢弃，这个背压策略必须显式设计
- 重启或迁移 actor 时要处理"旧实例仍在处理消息"的窗口

## 替代方案

- `pattern.concurrent.pipeline` — actor 是"谁拥有状态"，pipeline 是"数据怎么流过处理阶段"；两者可以组合。
- `pattern.gof.behavioral.mediator` — 中介者协调多个对象的交互（通常是同步的），actor 用消息解耦并提供并发隔离。

## 测试说明

- 单 actor 单元测试：直接调用消息处理函数，断言状态与回复
- 顺序测试：发送一串消息，断言最终状态（actor 的关键不变式是消息顺序决定结果）
- 背压测试：邮箱满时断言发送方的行为符合设计（阻塞/丢弃/拒绝）
- 并发测试：多发送方并发投递，断言无数据竞争（TSAN）与无消息丢失
- 恢复测试：actor 崩溃重启后，断言状态能从持久化恢复或明确丢失

## 实现注意

- actor 的价值在"状态归属清晰"，不是"性能更好"；消息传递通常比共享内存慢
- Rust 中可用 `std::sync::mpsc` + `thread` 手搭简单 actor，注意 channel 是 MPMC 的，actor 处理仍是串行的
- 消息类型应显式（枚举），避免用字符串或动态类型传递
- 不要在 actor 里持有全局可变状态或直接调用阻塞网络客户端而不做异步化
