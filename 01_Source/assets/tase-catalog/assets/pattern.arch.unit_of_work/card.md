# 工作单元（Unit of Work）

- 资产 ID：`pattern.arch.unit_of_work`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`UnitOfWork`、`工作单元`、`unit of work`

## 一句话定位

为一次业务操作划定事务边界：期间的所有改动先记在变更集里，结束时一次性提交，失败则整体回滚。

一次下单要同时改订单表、库存表、优惠券表；中间任何一步失败都要全部回滚，而手写 `begin/commit` 容易漏在错误路径上。

## 典型源文件形状

```rust
pub trait UnitOfWork: Send {
    fn orders(&mut self) -> &mut dyn OrderRepository;
    fn inventory(&mut self) -> &mut dyn InventoryRepository;
    fn commit(self: Box<Self>) -> Result<(), UowError>;
}

// 使用：任一步失败即 drop，事务随之回滚
let mut uow = pool.begin_unit_of_work();
uow.orders().save(&order)?;
uow.inventory().reserve(&sku, qty)?;
Box::new(uow).commit()?;
```

## 适用条件

- 一次业务操作涉及多个聚合或多个仓储的写
- 需要"全部成功或全部失败"的原子性
- 希望避免业务代码里散落 `begin/commit/rollback`
- 需要把变更跟踪与提交顺序集中管理
- 系统边界：事务边界只覆盖单个数据库实例内的本地事务；跨服务的一致性不在边界内（由 Saga 或事务发件箱负责）。

## 反例

- 单表单写——直接用数据库事务即可，不必引入工作单元抽象
- 跨服务写——本地工作单元保证不了跨服务原子性，应使用 Saga 或事务发件箱
- 只读操作——工作单元没有意义
- 长事务（人在回路里确认）——事务持有锁与连接的时间不可控，应拆成 Saga

## 并发风险

- 工作单元通常绑定一个连接并持有事务，因此它不是 `Sync` 的，只能串行使用
- 工作单元的生命周期必须严格限定在一次操作内；把它放进长生命周期的结构体（如全局单例）会导致连接被长期占用
- 并发修改同一聚合时，工作单元的事务隔离级别决定可见性；乐观锁（版本号）比行锁更适合长事务
- 在提交前读取的数据可能已被其它事务修改（写偏差），需要在提交时做校验或用乐观并发控制
- 把工作单元跨线程传递需要 `Send`，但绝不能跨线程同时使用同一个实例

## 替代方案

- `pattern.integration.transactional_outbox` — 需要"本地提交 + 异步可靠通知外部"时用事务发件箱；它解决的是跨系统一致性而非本地原子性。
- `pattern.integration.saga` — 跨多个独立系统的长事务用 Saga 编排补偿，而不是一个本地工作单元。

## 测试说明

- 用真实数据库测提交路径：断言所有改动一起可见
- 测回滚路径：注入中途失败，断言没有任何改动落库
- 断言回滚后工作单元不可再次提交（一次提交语义）
- 并发测试：两个工作单元同时改同一聚合，断言乐观锁冲突被正确报告

## 实现注意

- 工作单元的事务边界应等于业务用例边界，而不是 HTTP 请求边界
- 不要把工作单元做成全局单例；它的价值在于"短生命周期、明确作用域"
- 提交时的校验（如版本号、唯一约束）不能省略，它是对并发的最后防线
- 在 Rust 中 `commit(self: Box<Self>)` 的写法能保证提交后不可复用，但要注意 API 可读性
