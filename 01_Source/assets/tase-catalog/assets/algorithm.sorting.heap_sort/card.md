# 堆排序（Heap Sort）

- 资产 ID：`algorithm.sorting.heap_sort`
- 类型：`algorithm`（算法）
- 分类：`sorting`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`heap_sort`、`堆排序`、`heapsort`

## 一句话定位

原地、不稳定但最坏情况有保证的排序：先把数组构造成堆，再反复取堆顶与末尾交换。

内存受限但又需要 O(n log n) 的最坏情况保证——归并需要 O(n) 额外空间，快速排序最坏可能退化。

## 典型源文件形状

```text
heap_sort(a):
    build_max_heap(a)          // 自底向上建堆：O(n)
    for end = len(a)-1 down to 1:
        swap(a[0], a[end])      // 把堆顶（最大值）换到末尾
        sift_down(a, 0, end)    // 恢复堆性质：O(log n)
```

## 适用条件

- 内存紧张、要求原地排序（O(1) 额外空间）
- 需要最坏情况 O(n log n) 的保证
- 不要求稳定性
- 数据量较大且比较成本高（比较次数可控）

## 反例

- 需要稳定排序——堆排序不满足
- 数据量小——插入排序更快
- 追求平均性能——快速排序或标准库 pdqsort 通常更快
- 数据已经有序——堆排序不会利用已有顺序（自底向上建堆已把顺序打乱）

## 并发风险

- 堆排序原地修改数组，天然不是并发安全的；共享数组上的堆排序需要独占访问
- 不同线程对不同切片各自排序是安全的
- 堆的 `sift_down` 路径是串行的，不存在可并行的分支
- 若把堆放进共享结构（如 `Arc<Mutex<Vec>>`），锁粒度覆盖整个排序过程，会成为并发瓶颈

## 替代方案

- `algorithm.sorting.merge_sort` — 需要稳定性或 O(n) 额外空间可接受时，归并排序是更好的选择。
- `algorithm.sorting.quick_sort` — 平均性能更好且常数更小，代价是最坏情况 O(n²)。

## 测试说明

- 与标准库 `sort_unstable` 交叉比较，断言结果集合一致
- 随机、已排序、逆序、全部相等、含重复值
- 空数组与单元素
- 建堆后的不变式测试：断言数组满足最大堆性质
- 性能回归：对固定规模记录耗时上限，防止实现退化为 O(n²)

## 实现注意

- 优先标准库：Rust 的 `slice::sort_unstable` 使用 pdqsort，比手写堆排序快且同样原地
- 复杂度：时间 O(n log n)（建堆 O(n) + n 次 O(log n) 的下沉），额外空间 O(1)
- 稳定性：不稳定，相等元素的相对顺序可能被交换改变
- 内存：原地，除递归/循环变量外无需额外数组；适合内存受限场景
- 溢出：计算下标时用 `usize` 并注意 `2*i+1` 可能溢出，优先用 `checked` 或改用 `i < len/2` 形式
- 极端输入：重复元素多时比较次数上升；建堆过程不受输入顺序影响（自底向上）
- 并发安全：原地修改，不是线程安全的共享操作；并发场景下每个线程应独占自己的数据
- 限制：缓存局部性差（跳跃访问），实际性能常低于快速排序
