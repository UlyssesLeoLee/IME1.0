# 迭代器（Iterator）

- 资产 ID：`pattern.gof.behavioral.iterator`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Iterator`、`迭代器模式`、`iterator pattern`

## 一句话定位

把"怎么遍历"封装成一条统一的流水线，调用方只表达"要什么"，不关心数据怎么存。

同一份数据存在数组、链表、数据库游标等多种形态，每种都要写一遍遍历逻辑，代码里出现大量重复的 `while` 循环。

## 典型源文件形状

```rust
pub struct TreeIter<'a> {
    stack: Vec<&'a Node>,
}

impl<'a> Iterator for TreeIter<'a> {
    type Item = &'a Node;
    fn next(&mut self) -> Option<Self::Item> {
        let node = self.stack.pop()?;
        self.stack.extend(node.children.iter().rev());
        Some(node)
    }
}
```

## 适用条件

- 同一聚合有多种存储表示，需要统一的遍历接口
- 遍历逻辑本身复杂（过滤、变换、惰性求值），希望可组合
- 希望把"取数据"与"处理数据"解耦，支持流式处理大集合
- 需要暴露只读遍历，避免调用方依赖内部结构

## 反例

- 只需要按下标取值——索引接口更符合使用方式
- 集合很小且要遍历多次——物化成 `Vec` 更省心也更快
- 遍历顺序需要随机跳变——迭代器的顺序模型不匹配
- 为了"面向接口"而给只有一个实现的集合定义 trait——过度抽象

## 并发风险

- 迭代器通常借用集合，迭代期间不能可变借用同一集合（Rust 借用检查器会挡住，但 `RefCell` 包装下会在运行期 panic）
- 若集合用 `Arc` 共享且迭代过程中可能被其它线程修改，需要快照或写锁；否则迭代结果不确定
- 惰性迭代器把工作推迟到消费点，错误也会延迟到消费时才出现——跨线程传递惰性迭代器要格外小心
- 迭代器若持有文件句柄或连接，忘记消费时资源释放会延后

## 替代方案

- `pattern.gof.structural.composite` — 当数据本身是树并且需要统一的操作接口时用组合；迭代器只负责访问，不负责行为。
- `pattern.gof.behavioral.visitor` — 当遍历的同时要按类型分派不同操作时，用访问者而不是给迭代器加一堆 `is_*` 方法。

## 测试说明

- 断言迭代顺序与预期一致（顺序是契约的一部分）
- 断言空集合时迭代器返回 `None` 且不 panic
- 测试迭代过程中修改集合的行为：在 Rust 中应表现为编译期拒绝或运行期明确报错，而不是未定义行为
- 对惰性迭代器测试"不消费就不执行"的语义（用副作用计数器）
- 测试迭代器是 `FusedIterator`（消费完后继续 `next` 仍返回 `None`）

## 实现注意

- Rust 标准库已把迭代器做成一等公民，优先用 `Iterator` 组合子而不是自己写迭代器类
- 惰性迭代器在长链上可能栈溢出（深递归 `map`/`filter`），必要时改写为显式循环
- 不要在迭代器里做副作用（写日志、发请求），除非明确设计为 effectful
- 需要并行遍历时用 rayon 之类的成熟库，而不是手写线程池
