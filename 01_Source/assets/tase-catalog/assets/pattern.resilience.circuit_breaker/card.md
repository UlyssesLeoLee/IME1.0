# 断路器（Circuit Breaker）

- 资产 ID：`pattern.resilience.circuit_breaker`
- 类型：`pattern`（设计模式）
- 分类：`resilience`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`CircuitBreaker`、`断路器`、`circuit breaker`

## 一句话定位

给不稳定的下游加一个"熔断开关"：连续失败到阈值就停止调用，冷却后放一个探针试试恢复没有。

下游变慢时，持续的重试与排队会把本服务自己的线程池、连接池全部占满，形成级联故障。

## 典型源文件形状

```rust
#[derive(PartialEq)]
pub enum BreakerState { Closed, Open { until: Instant }, HalfOpen }

pub struct CircuitBreaker {
    state: Mutex<BreakerState>,
    failures: u32,
    threshold: u32,
    cooldown: Duration,
}

impl CircuitBreaker {
    pub fn allow(&self) -> bool { /* Closed → true；Open 未到期 → false */ }
    pub fn record_success(&self) { /* 重置计数 */ }
    pub fn record_failure(&self) { /* 计数并可能转入 Open */ }
}
```

## 适用条件

- 调用外部依赖（HTTP、数据库、缓存）且该依赖可能长时间不可用
- 希望快速失败而不是排队等超时
- 有降级方案（缓存、默认值、稍后重试）
- 资源紧张，不能让大量请求堆积在失败的下游上
- 系统边界：只对被它包裹的那条调用路径生效，不覆盖同一进程内其它路径对同一依赖的调用，也不能替代超时、连接池与限流。

## 反例

- 依赖是本地函数调用、几乎不会失败——断路器没有意义
- 下游故障是业务常态（如库存服务经常超时）——应该改接口或改容量，而不是靠熔断
- 没有降级方案时，熔断只是把"慢失败"变成"快失败"，对用户体验未必更好
- 所有下游共用一个断路器——会把一个依赖的故障传染给其它调用路径

## 并发风险

- 状态转换必须是原子的：多个线程同时观察到"Closed"会一起冲向下游
- 使用 `Mutex` 保护状态时不要在持锁状态下做网络调用，否则会阻塞所有调用者
- 半开状态只允许有限数量的探针请求（不是一次），否则下游刚恢复就被再次打垮
- 计数窗口要有时间维度（滑动窗口），否则"很久以前的失败"仍会触发熔断
- 断路器实例通常按"调用点 + 下游"划分，而不是全局一个
- 与重试组合时要注意：断路器打开后重试应立即失败，否则重试会绕过熔断的意义

## 替代方案

- `pattern.resilience.bulkhead` — 断路器减少对坏下游的调用，隔离舱限制每个下游占用的资源，两者常配合。
- `pattern.resilience.retry_with_exponential_backoff_and_jitter` — 重试处理"偶发抖动"，断路器处理"持续不可用"；没有断路器的重试会在故障期间放大流量。

## 测试说明

- 状态机测试：失败达阈值 → Open；冷却到期 → HalfOpen；探针成功 → Closed
- 并发测试：多线程同时失败，断言只有一次状态转换生效且计数不丢失
- 断言 Open 状态下不会真的调用下游（用假下游计数）
- 断言探针失败后回到 Open 且冷却时间被重置
- 断言降级路径被正确使用（返回缓存值或明确错误，而不是 panic）

## 实现注意

- 断路器的阈值必须结合真实流量标定；默认值（连续 5 次失败、冷却 30 秒）只是起点
- 要区分"下游真的坏了"与"请求本身非法"，后者不应计入失败率
- 断路器状态要有指标（打开次数、打开时长），否则无法判断它是否在帮倒忙
- 设计书要求：反例、许可与风险必须随机器结果返回，防止 Agent 无条件套用
