# 命令查询职责分离（CQRS）

- 资产 ID：`pattern.arch.cqrs`
- 类型：`pattern`（设计模式）
- 分类：`arch`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`CQRS`、`命令查询职责分离`、`command query responsibility segregation`

## 一句话定位

用两套模型分别服务"改"和"查"，写侧保持一致，读侧按查询需求自由造型。

同一个大表既要支撑复杂写入（保持范式、约束）又要支撑多种报表查询（多表拼接、聚合），单一模型两头不讨好。

## 典型源文件形状

```rust
// 写侧：只做状态变更
pub struct PlaceOrder { pub order_id: OrderId, pub items: Vec<Item> }
impl PlaceOrder {
    pub fn handle(self, uow: &mut dyn UnitOfWork) -> Result<(), AppError> {
        uow.orders().save(&Order::new(self.order_id, self.items))?;
        Ok(())
    }
}

// 读侧：面向查询的投影
pub struct OrderSummaryView { pub customer: String, pub total: f64 }
```

## 适用条件

- 写模型与读模型的形状差异很大
- 读负载远高于写负载，或需要复杂报表
- 需要独立扩展读侧（加副本、加索引、加缓存）
- 团队能够承担最终一致性的产品语义
- 系统边界：分离的是读写模型与两者之间的同步链路，不提供分布式事务，也不改变底层存储的事务能力；一致性窗口是产品必须接受的边界条件。

## 反例

- 读写都简单——拆分只带来同步延迟与运维复杂度
- 业务需要强一致的读后写——必须额外引入"等待投影追上"的机制，复杂度反超收益
- 团队缺少异步与事件驱动经验——CQRS 的调试门槛很高
- 只是为了"性能"而在查询里 JOIN 很多表——先加索引或建读副本更直接

## 并发风险

- 写侧并发通常用乐观锁；读侧副本与写侧存在复制延迟，必须向产品侧声明一致性窗口
- 投影消费者必须幂等：同一事件被重复投递时不得重复计入
- 多写者并发更新同一聚合时，要用版本号或事件序号做冲突检测，不能依赖最后写入者获胜
- 读模型重建（重新投影全量事件）期间不能与增量投影并发写同一投影表，否则数据不一致
- 事件顺序在分区消费时可能被打乱，投影需能容忍乱序（按版本号幂等写入）

## 替代方案

- `pattern.arch.event_sourcing` — CQRS 的读侧通常由事件驱动，事件溯源是"以事件为唯一真相"；两者常配合但不等同。
- `pattern.integration.read_copy_update` — 读副本更新是 CQRS 读侧的一种实现手段（从主库复制到查询库），范围更窄。

## 测试说明

- 写侧测试：断言命令被拒绝的场景（不变量、权限、状态机非法转换）
- 读侧测试：断言查询结果与给定写侧状态一致
- 一致性测试：写入后等待投影追上，断言读侧最终可见（带超时而非固定 sleep）
- 投影幂等测试：重复投递同一事件，断言读侧结果不变
- 重建测试：从头重放事件，断言重建后的投影与增量投影一致

## 实现注意

- CQRS 是"读写分离"的架构决策，不等于"读写分离部署"；最轻的形态可以同库不同模型
- 必须把最终一致性窗口当作产品需求写清楚，不能当作技术细节
- 读侧可以是简单 SQL 查询视图，不必上专门的读模型存储
- CQRS 的复杂度主要在同步链路与运维，不要把它当成性能银弹
