# Rabin-Karp 字符串匹配（Rabin–Karp Algorithm）

- 资产 ID：`algorithm.string.rabin_karp`
- 类型：`algorithm`（算法）
- 分类：`string`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`rabin_karp`、`RabinKarp`、`滚动哈希`、`rolling hash`

## 一句话定位

给窗口算一个滚动哈希，哈希相同才做真正的字符比较，于是平均只需常数次比较。

在数 GB 的日志里查找若干个固定标记，滚动哈希可以避免每次都逐字符比对。

## 典型源文件形状

```text
rabin_karp(text, pattern, base, mod):
    m = len(pattern); n = len(text)
    if m > n: return no match
    h_pattern = hash(pattern)
    h_window  = hash(text[0..m])
    pow_b = base^(m-1) mod mod
    for i in 0..n-m:
        if h_window == h_pattern and text[i..i+m] == pattern:   // 必须二次校验
            report match at i
        h_window = ((h_window - text[i]*pow_b) * base + text[i+m]) mod mod
```

## 适用条件

- 需要滚动计算子串哈希（很多场景本身就需要哈希）
- 文本与模式都很长，且模式数量少
- 模式串长度大于某个阈值时的多模式匹配预处理
- 指纹比较、可疑输入快速筛除（先用哈希缩小候选）

## 反例

- 单模式且要求确定性——KMP 保证最坏 O(n+m)，Rabin-Karp 只是期望
- 短模式短文本——朴素比较常数更小
- 对碰撞敏感且不愿二次校验——哈希匹配会误报
- 需要子串哈希但不需要匹配——直接用滚动哈希本身即可

## 并发风险

- 滚动哈希是无状态的（除当前窗口哈希外不写共享数据），天然可并发扫描不同区间
- 若用 `HashMap` 预存模式哈希，查找阶段需要只读共享（`HashMap` 的 `get` 是并发安全的，前提是构建后不再修改）
- 并行分片扫描时每个分片要处理跨界窗口（多算 m-1 个字符）
- 哈希随机种子要在进程内固定，否则不同线程算出的哈希不一致

## 替代方案

- `algorithm.string.kmp` — 单模式匹配优先 KMP，确定性且无需碰撞处理。
- `algorithm.string.z_algorithm` — 需要所有后缀的匹配长度时用 Z 算法。

## 测试说明

- 与朴素匹配交叉比较，断言所有匹配位置一致
- 构造碰撞用例（人为选择 base/mod 制造相同哈希），断言二次校验仍能正确报告
- 模式串为空、文本为空、模式长于文本
- 单字符模式、重复字符
- 非 ASCII 文本（按字节处理时的行为要明确）

## 实现注意

- 优先标准库/成熟库：需要滚动哈希时优先用成熟实现（如 `twox-hash` 等 crate），引入前核查许可
- 复杂度：期望 O(n + m)；最坏 O(n·m)（大量碰撞时），这是它相对 KMP 的劣势
- 稳定性：不适用
- 内存：O(1) 额外空间（模式哈希表除外）
- 溢出：模乘必须用足够宽的类型或 128 位中间值（`u64` 乘法会溢出），这是最常见的实现 bug
- 极端输入：全部相同字符、刻意构造的碰撞串、模数较小
- 并发安全：滚动计算本身无共享状态；模式哈希表需构建后只读
- 限制：存在哈希碰撞，必须做二次校验；最坏情况退化
