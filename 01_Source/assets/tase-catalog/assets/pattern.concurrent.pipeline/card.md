# 流水线（Pipeline）

- 资产 ID：`pattern.concurrent.pipeline`
- 类型：`pattern`（设计模式）
- 分类：`concurrent`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Pipeline`、`流水线`、`pipeline pattern`、`数据流水线`

## 一句话定位

把一条长处理链切成若干同构阶段，让数据像流水线上的工件一样逐段前进，各段可以各自加速。

视频转码要"读取 → 解码 → 滤镜 → 编码 → 写出"，串行做每帧都得等前一步完成，CPU 也没吃满。

## 典型源文件形状

```rust
pub trait Stage: Send {
    type Input;
    type Output;
    fn run(&mut self, item: Self::Input) -> Result<Self::Output, StageError>;
}

// 阶段之间用有界通道连接，形成流水线
let (tx_frames, rx_frames) = sync_channel(8);
let decoder = thread::spawn(move || decode_loop(rx_frames, tx_frames));
```

## 适用条件

- 处理可拆成多个职责清晰的阶段
- 各阶段速率不同，需要解耦与背压
- 单个阶段的吞吐是瓶颈，需要并行
- 阶段可以独立测试（输入输出是明确的数据）
- 系统边界：阶段内部的事务性与顺序保证由各阶段自己负责；跨阶段的端到端语义（"这条数据处理完代表什么"）不在边界内。

## 反例

- 阶段之间需要互相回看或共享可变状态——流水线的单向假设被破坏
- 阶段数很少——顺序调用加函数组合更简单
- 每项数据都很小且处理极快——线程间传递开销超过收益
- 需要全局顺序保证且无法分批——流水线不保证跨批次的全局顺序

## 并发风险

- 阶段之间必须用有界通道，否则慢阶段会导致内存无限增长
- 每个阶段的并发度独立可调：慢阶段加实例，快阶段单实例即可
- 错误处理策略要显式：某阶段失败时是停止整条流水线、跳过该条目还是重试
- 阶段之间传递的数据应尽量小；大对象宜用引用计数共享，避免反复拷贝
- 流水线的整体背压由最慢阶段决定，容量规划要按最慢阶段算
- 关闭顺序要正确：上游结束后要关闭下游的通道，否则下游会永远等待

## 替代方案

- `pattern.gof.behavioral.iterator` — 迭代器链能表达同样的阶段组合，但它是单线程惰性的；需要跨线程并行时用流水线。
- `pattern.concurrent.actor` — 流水线是"数据流过阶段"，actor 是"消息送到状态拥有者"，常组合使用。

## 测试说明

- 每个阶段单独测：给定输入断言输出
- 端到端测：串联所有阶段，断言最终结果与顺序
- 背压测试：注入慢阶段，断言上游会被阻塞而不是无限堆积内存
- 错误测试：某阶段失败，断言流水线的失败策略（停止/跳过/重试）符合文档
- 关闭测试：上游结束后断言所有阶段能正常退出（不挂死）

## 实现注意

- 流水线与 Unix 管道思想一致，但编程语言里的实现需要显式处理错误与关闭
- 阶段数量要与团队能观测的粒度匹配；阶段太多会让延迟定位困难
- 背压是最容易漏掉的设计点：没有有界缓冲的流水线在压力下会 OOM
- 每阶段的指标（吞吐、延迟、错误率）要单独采集，否则无法定位瓶颈
