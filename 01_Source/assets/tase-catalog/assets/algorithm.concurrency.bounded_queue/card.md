# 有界队列（Bounded Queue）

- 资产 ID：`algorithm.concurrency.bounded_queue`
- 类型：`algorithm`（算法）
- 分类：`concurrency`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`bounded_queue`、`有界队列`、`bounded buffer`、`环形缓冲`

## 一句话定位

一个容量固定的先进先出缓冲区：满了让生产者等，空了让消费者等，用等待代替无限堆积。

把数据从 8 个采集线程送到 2 个写入线程，无界队列会在写入变慢时把内存吃光。

## 典型源文件形状

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::sync_channel::<Item>(64);   // 有界通道：容量 64

for worker in 0..8 {
    let tx = tx.clone();
    thread::spawn(move || {
        for item in produce(worker) {
            tx.send(item).unwrap();   // 队列满时阻塞，形成背压
        }
    });
}
drop(tx);
for item in rx { write(item); }
```

## 适用条件

- 生产速度可能超过消费速度，需要限制内存增长
- 需要把背压传导回生产者（让它降速）
- 缓冲容量可估计（有明确的速率与延迟目标）
- 需要保序（FIFO）

## 反例

- 生产与消费速率稳定匹配——无界队列更简单
- 需要处理超出内存可承载的积压——应引入磁盘型队列
- 丢弃策略比阻塞更合适（如遥测采样）——应使用显式的丢弃型队列
- 容量需要动态调整——固定容量的设计前提不成立

## 并发风险

- 有界队列本身就是并发原语：入队/出队必须原子，且"等待"与"唤醒"要正确配对
- 阻塞式队列在生产线程多于消费者时会形成背压，但也可能导致上游线程全部卡住
- 容量为 0 的同步通道（`sync_channel(0)`）是严格握手，吞吐最低但语义最强
- 队列满时的策略有三种：阻塞（背压）、拒绝（快速失败）、丢弃（采样），必须显式选择
- 关闭协议要明确：所有生产者 `drop` 发送端后，消费者才能正常收到结束信号
- 多消费者场景要注意公平性，否则某些消费者可能长期取不到数据

## 替代方案

- `pattern.concurrent.pipeline` — 流水线是由多个有界缓冲连接起来的处理阶段。
- `pattern.resilience.rate_limiter` — 限流器限制的是请求速率，有界队列限制的是在途数量。

## 测试说明

- 断言 FIFO 顺序：入队顺序与出队顺序一致
- 容量为 1 与容量为 0 的边界行为
- 生产者多于消费者时断言生产者被阻塞（背压生效）
- 关闭后消费者能收到结束信号并退出（不死锁）
- 并发测试：多生产者多消费者下元素不丢不重（用计数校验）
- 断言队列满时的策略行为符合文档

## 实现注意

- 优先标准库：Rust 的 `std::sync::mpsc::sync_channel(n)` 是有界通道；跨线程共享用 `crossbeam-channel`（MIT/Apache-2.0），引入前需核查许可
- 复杂度：入队出队 O(1)（摊还），空间 O(容量)
- 稳定性：不适用
- 内存：容量固定，内存占用可预测——这正是有界队列的核心价值
- 溢出：容量与计数用 `usize`；`sync_channel(0)` 是合法的同步通道
- 极端输入：容量 0、容量 1、生产者远多于消费者、瞬时突发流量
- 并发安全：队列本身即并发原语；内部的锁/信号量实现必须正确配对唤醒
- 限制：固定容量；丢弃策略会丢数据；跨进程需用消息中间件而非内存队列
