# 哈希表（Hash Table）

- 资产 ID：`algorithm.datastructure.hash_table`
- 类型：`algorithm`（算法）
- 分类：`datastructure`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`hash_table`、`哈希表`、`散列表`、`hash map`

## 一句话定位

把键哈希成桶下标，用开槽或链地址解决冲突，用装填因子控制冲突概率。

在百万条记录里按键查找，线性扫描要百万次比较，哈希表只需一次哈希加常数次探测。

## 典型源文件形状

```rust
use std::collections::HashMap;

let mut counts: HashMap<&str, u32> = HashMap::new();
counts.insert("a", 1);
let v = counts.get("a");               // O(1) 期望
let old = counts.insert("a", 2);        // 返回旧值，便于覆盖计数
```

## 适用条件

- 按键做精确查找
- 键空间大且无序需求
- 插入删除频繁
- 需要 O(1) 级别的查找（期望）

## 反例

- 需要有序遍历或范围查询——用有序结构（B 树、跳表）
- 键数量很小——线性扫描或有序数组更简单
- 攻击者可控输入且哈希可预测——需要加盐随机哈希（DoS 防护）
- 键是复杂对象且哈希昂贵——要评估哈希成本是否抵消收益

## 并发风险

- 标准哈希表不是线程安全的共享结构
- 并发方案：分片加锁（每片独立锁，竞争下降）、读写锁（读多写少时）、或每线程一份
- Rust 的 `RwLock<HashMap>` 适合读多写少，但写会阻塞所有读者
- 迭代一个正被其它线程修改的哈希表会 panic（Rust 会检测到变化）——需快照或锁保护
- 扩容（rehash）期间需要独占访问，否则并发读写可能看到不一致状态

## 替代方案

- `algorithm.datastructure.binary_heap` — 需要取最值时用堆；哈希表不提供最值语义。
- `algorithm.datastructure.lru_cache` — 需要在 O(1) 淘汰时用 LRU，它内部就是哈希表加链表。

## 测试说明

- 插入、查找、删除、覆盖的行为正确
- 不存在键的查找返回 None 而不 panic
- 大量键触发多次扩容后仍然正确
- 自定义键类型：哈希与相等必须一致（否则会查不到）
- 含 `f64::NAN` 的键（相等与哈希的特殊性）
- 并发测试：多线程插入与读取不 panic、不丢数据

## 实现注意

- 优先标准库：Rust 的 `std::collections::HashMap`（SipHash-1-3，默认随机种子抗 HashDoS）与 `BTreeMap`（有序）已经成熟，不要手写
- 复杂度：期望 O(1) 每次操作，最坏 O(n)（全部冲突），空间 O(n)
- 稳定性：不适用（遍历顺序不确定）
- 内存：约每个条目 2-3 倍键值开销（哈希表元数据 + 负载因子预留空间）
- 溢出：容量与长度用 `usize`；哈希计算本身要保证对相同键恒定（不能用随机源）
- 极端输入：全部键哈希冲突、容量增长到极大、`f64::NAN` 作键、零-sized 类型键
- 并发安全：非线程安全；并发写入需分片或锁，迭代与修改并发会 panic
- 限制：无序；最坏情况退化；自定义键必须保证 `Hash` 与 `Eq` 一致
