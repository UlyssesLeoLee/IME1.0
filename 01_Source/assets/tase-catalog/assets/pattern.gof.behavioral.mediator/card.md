# 中介者（Mediator）

- 资产 ID：`pattern.gof.behavioral.mediator`
- 类型：`pattern`（设计模式）
- 分类：`behavioral`
- 版本：`1.0.0`
- 状态：`DOCUMENTED`（知识卡已成文，尚未经人工审阅；本资产没有任何已认证的语言实现）
- 别名：`Mediator`、`中介者模式`、`mediator pattern`

## 一句话定位

把"一群对象之间乱麻般的互相调用"收拢到一个协调者里，让每个对象只跟协调者说话。

聊天群里的成员互相引用、互相调用，任何一个人改逻辑都要通知所有其他人，代码里满是循环依赖。

## 典型源文件形状

```rust
pub trait Colleague { fn notify(&mut self, event: &str, m: &mut Mediator); }

pub struct Mediator { pub log: Vec<String> }

impl Mediator {
    pub fn route(&mut self, from: &str, event: &str, peers: &mut Vec<Box<dyn Colleague>>) {
        self.log.push(format!("{from} -> {event}"));
        for p in peers.iter_mut() { p.notify(event, self); }
    }
}
```

## 适用条件

- 一组对象之间的交互关系密集且经常变化（GUI 对话框、工作流节点、聊天系统）
- 希望把交互规则集中到一个地方，便于理解与测试
- 各个同事对象应能独立复用，不该互相认识
- 直接引用导致循环依赖，需要打断

## 反例

- 交互是线性的两两调用——直接调用更短
- 协调逻辑本身是可复用的策略——那应该抽成策略而不是中介者
- 中介者变成了所有逻辑的堆放处——此时它其实是"上帝对象"，应该拆分
- 同事对象之间确实存在稳定的一对一关系——中介者增加了无谓的间接

## 并发风险

- 中介者通常持有可变状态（队列、登记表、对话历史），共享时必须加锁；建议用 `Mutex<Mediator>` 或消息队列把状态移出
- 若中介者通过回调访问同事，回调期间持锁容易死锁；应先复制出待通知列表，释放锁后再回调
- 同事对象在回调中再次调用中介者会产生重入，需明确是否允许与如何处理
- 把中介者放在单线程 actor 中是最简单的并发方案（见 actor 资产）

## 替代方案

- `pattern.gof.structural.facade` — 外观面向客户端简化调用，中介者协调内部对象之间的交互；一个对外、一个对内。
- `pattern.gof.behavioral.observer` — 当关系是"一对多的广播"而非"多对多的协商"时，观察者更简单。

## 测试说明

- 对每个交互场景写一条用例，断言参与的同事与顺序（用记录型假同事）
- 测试一个同事缺席或拒绝时的行为（中介者应明确处理，而不是崩溃）
- 断言同事之间没有互相引用（用代码审查或依赖检查规则保证）
- 对中介者的并发用例：多线程投递事件，断言没有数据竞争且处理顺序可解释

## 实现注意

- 中介者容易膨胀为"上帝对象"；当它超过若干职责时，按关注点拆成多个协调者
- 与事件总线/发布订阅相比，中介者是同步、直接、无广播语义的
- 把协调规则写成数据（状态机表）往往比写代码更易测试
- Rust 中可用 `enum` 事件 + `match` 实现轻量中介者，避免 trait 对象的动态派发
